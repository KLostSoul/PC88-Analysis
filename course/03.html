먼저 큰 흐름

처음에는 “데이터가 어디에서 와서 어디로 가는가”만 본다

게임을 실행하면 디스크에 저장된 데이터가 기계 안으로 들어와 메모리에 놓이고, 화면에 글자를 그릴 때는 글자 모양을 담아 둔 곳에서 점 모양 데이터를 가져옵니다. 처음부터 주소 이름과 하드웨어 이름을 외우지 말고, 먼저 이 두 흐름만 머릿속에 그립니다.

이제 이름을 붙이면: 뒤에서 이 흐름에 FDD, FDC, RAM, D88, Kanji ROM 같은 정확한 이름을 하나씩 붙입니다. 지금 단계에서는 이름보다 “디스크의 데이터가 메모리로 들어온다”와 “글자 모양 데이터를 읽어 화면에 그린다”만 이해하면 됩니다.

실제로 움직이는 것

1. 플로피 안에서는 얇은 자기 원판이 계속 빙글빙글 돈다

플로피 안에는 얇은 원판이 들어 있고, 게임을 읽는 동안 이 원판이 회전합니다. 원판 옆의 작은 읽기/쓰기 장치는 원판과 함께 빙글빙글 돌지 않습니다. 그 장치는 한 위치에 머물러 있고, 원판에 기록된 내용이 그 아래를 차례로 지나갑니다.

이제 이름을 붙이면: 원판의 같은 거리에서 한 바퀴 이어지는 둥근 기록 길을 Track이라고 하고, 그 기록을 읽고 쓰는 장치를 Head라고 부릅니다. 한 Track 안을 나눈 작은 기록 구간은 뒤에서 Sector라고 부릅니다.

Head 아래를 지나가는 기록 구간

흔한 오해: Head가 원판 둘레를 따라 도는 것이 아닙니다. 이 Lab에서는 Head가 고정되어 있고, 원판에 기록된 여러 구간이 차례로 Head 아래를 지나갑니다. 이 작은 기록 구간의 정확한 이름과 번호는 4~5장에서 붙입니다.
읽는 위치 바꾸기

2. 다른 둥근 기록 줄을 읽으려면 읽는 장치를 안쪽이나 바깥쪽으로 옮겨야 한다

원판에는 바깥쪽부터 안쪽까지 여러 개의 둥근 기록 줄이 있습니다. 읽는 장치가 바깥쪽 줄 위에 있는데 안쪽 줄의 데이터를 읽고 싶다면, 원판이 계속 도는 것만으로는 안 됩니다. 읽는 장치 자체가 원판 중심 쪽으로 이동해서 원하는 줄 위에 와야 합니다.

이제 이름을 붙이면: 이 둥근 기록 줄이 Track이고, Head를 원하는 Track의 반지름 위치로 옮기는 동작을 SEEK라고 부릅니다. SEEK가 끝난 뒤에도 원하는 Sector가 Head 아래로 돌아올 때까지 원판 회전을 기다릴 수 있습니다.

원판의 바깥쪽에서 중심까지 한 줄로 펼쳐서 본다

둥근 원판을 그대로 보면 읽는 장치가 안쪽·바깥쪽으로 움직인다는 사실이 잘 보이지 않습니다. 그래서 아래에서는 원판의 바깥쪽 가장자리에서 중심까지를 한 줄로 펼쳐서 생각합니다.

안쪽·바깥쪽의 다른 기록 줄

장치를 옮겨야 합니다. 읽기/쓰기 장치를 원하는 기록 줄의 반지름 위치로 이동시킵니다. 이 동작이 SEEK입니다.

디스크의 다른 면

읽기/쓰기 장치를 안쪽·바깥쪽으로 옮기는 문제와는 다릅니다. 한 장의 디스크가 양쪽 면을 어떻게 읽는지는 다음 장에서 따로 설명합니다.

핵심은 두 동작을 따로 생각하는 것이다

먼저 — 읽는 위치를 맞춘다읽고 싶은 둥근 기록 줄이 현재 위치와 다르면 읽는 장치를 안쪽이나 바깥쪽으로 옮겨 그 줄의 반지름 위치에 맞춥니다. 이 이동을 SEEK라고 합니다.
↓
그 다음 — 원판이 돌아오기를 기다린다원하는 기록 줄에 도착한 뒤에는 읽는 장치를 더 옮기지 않습니다. 원판이 돌면서 원하는 기록 구간이 장치 아래로 올 때까지 기다리고, 식별 정보가 맞으면 실제 데이터를 읽습니다.
가장 중요한 구분: SEEK = Track 위치를 맞추는 동작입니다. SEEK가 끝났다고 해서 원하는 Sector의 Data까지 이미 읽은 것은 아닙니다. Track에 도착한 뒤에도 원판 회전과 Sector ID 탐색이 이어집니다.
디스크의 양쪽 면

3. 양면 플로피는 한 장의 디스크에서 위쪽과 아래쪽 두 면을 모두 읽고 쓸 수 있다

얇은 자기 디스크에는 앞뒤 두 면이 있습니다. 양면으로 사용하는 플로피에서는 두 면 모두에 데이터를 기록할 수 있습니다. 드라이브에는 각 면의 기록을 읽고 쓰는 장치가 하나씩 있으며, 두 장치는 한 묶음으로 함께 안쪽이나 바깥쪽으로 움직입니다.

먼저 이것만 이해: 디스크가 두 장 있는 것이 아닙니다. 한 장의 얇은 자기 디스크에 기록할 수 있는 면이 두 곳 있고, 각 면을 담당하는 읽기/쓰기 장치도 하나씩 있습니다.

Lab 2 — 한 장의 디스크에서 위·아래 두 면을 어떻게 읽는지 보기

버튼을 누르면서 한 장의 디스크 몸체 → 그 디스크의 위·아래 기록면 → 각 면을 담당하는 두 Head → 두 Head가 함께 이동하는 구조 순서로 봅니다. 여기서 위/아래는 이해를 위한 그림 배치입니다.

위에서 본 모습
옆에서 본 같은 디스크
회색 몸체옆에서 본 한 장의 얇은 자기 디스크입니다. 두 개의 디스크를 그린 것이 아닙니다.
파란 위·아래 가장자리같은 디스크의 위쪽 기록면과 아래쪽 기록면을 강조한 것입니다.
검은 삼각형과 연결부각 면을 읽는 두 Head와, 두 Head가 함께 움직인다는 것을 설명하기 위한 단순화된 표시입니다.
이제 이름을 붙이면: 디스크의 두 기록면을 Side 0 / Side 1, 각 면을 읽고 쓰는 장치를 Head 0 / Head 1이라고 부릅니다. 한 면에서 같은 반지름을 따라 이어지는 둥근 기록 줄이 Track이고, 양쪽 면에서 같은 반지름 위치의 Track들을 묶어 부르는 이름이 Cylinder입니다.

Side와 Head는 같은 것이 아니다

Side는 데이터를 기록하는 면이고 Head는 그 면의 자기 기록을 읽고 쓰는 장치입니다. 따라서 “Side 0 = Head 0”이 아니라 “Side 0을 Head 0이 담당한다”고 이해합니다.

Cylinder는 실제 원통 부품이 아니다

두 Head가 같은 반지름 위치로 함께 움직이므로, 양쪽 면에서 그 위치의 Track들을 하나의 묶음으로 부릅니다. 이 논리적 묶음이 Cylinder입니다.

그림의 위/아래: 회색 몸체 하나가 한 장의 자기 디스크이고, 그 윗면과 아랫면을 서로 다른 기록면으로 표시했습니다. 여기서 위/아래는 설명을 위한 그림 배치이며, 실제 분석의 핵심은 두 기록면과 두 Head를 서로 구분한다는 점입니다.
기록을 나누는 방법

4. 한 바퀴의 기록은 작은 구간들로 나뉘고, 각 구간에는 “이게 어느 구간인지”와 실제 데이터가 함께 들어 있다

둥근 기록 줄 한 바퀴 전체를 한 덩어리로만 쓰면 원하는 데이터를 찾기 어렵습니다. 그래서 기록을 여러 작은 구간으로 나누고, 각 구간에는 자기 자신을 식별하는 정보와 실제 데이터를 함께 둡니다.

이제 이름을 붙이면: 이 작은 기록 구간을 Sector라고 합니다. Sector를 식별하는 부분은 ID Field, 실제 데이터가 들어 있는 부분은 Data Field라고 합니다.

원하는 구간 찾기

5. 원하는 데이터 구간을 찾으려면 그 구간에 적힌 네 가지 번호를 하나씩 대조한다

디스크를 읽는 제어 장치는 “지금 지나가는 구간이 내가 찾는 구간인가?”를 확인해야 합니다. 그래서 요청할 때 네 가지 값을 함께 주고, 원판이 돌면서 발견되는 각 구간의 네 값을 하나씩 비교합니다. 하나라도 다르면 그 구간은 지나치고 다음 구간을 기다립니다.

이제 이름을 붙이면: 이 네 값을 C/H/R/N이라고 씁니다. C는 어느 원통 위치인지, H는 어느 면인지, R은 그 Track 안에서 어떤 Sector인지, N은 데이터 크기를 나타내는 코드입니다. 이 비교를 실제로 수행하는 디스크 제어 장치를 FDC라고 부릅니다.
기호뜻이 Lab에서 보는 역할

HHead ID요청값과 읽힌 ID의 H가 같은지 확인
RRecord ID같은 Track 안에서 어느 Sector를 원하는지 구분

왜 이 예제에서는 R만 달라지는가? 같은 Track에 같은 크기로 포맷된 일반적인 Sector들을 비교하는 상황을 단순화했기 때문입니다. 실제 ID에서 C, H, N 가운데 하나라도 요청값과 다르면 그 ID 역시 목표와 일치하지 않습니다.
C/H와 물리 위치를 동일시하지 말 것: 정상 포맷에서는 실제 위치와 자연스럽게 대응하는 경우가 많지만 C/H는 Sector의 ID Field에 기록된 값입니다. 특수 포맷에서는 물리 위치와 다른 ID도 가능합니다.
데이터 길이

6. 네 가지 번호 중 하나는 “데이터가 몇 바이트인지”를 직접 쓰지 않고 코드로 나타낸다

Sector마다 저장되는 데이터 양이 다를 수 있습니다. 그런데 식별 정보에는 256, 512 같은 바이트 수를 그대로 적는 대신 작은 숫자 하나를 넣고, 그 숫자로 실제 크기를 계산하는 방식을 씁니다.

이제 이름을 붙이면: C/H/R/N 가운데 마지막 값 N이 바로 Size Code입니다. 기본 해석은 128 × 2^N이며, 예를 들어 N=1이면 256byte입니다.
nominal sector size = 128 × 2N = 128 << N
N계산표준 Sector Data 크기
0128 × 1128 bytes
1128 × 2256 bytes
2128 × 4512 bytes
3128 × 81024 bytes
예: ID Field가 N=1이라면 nominal Sector Data 크기는 128 << 1 = 256 bytes입니다. N 자체가 256을 뜻하는 것은 아닙니다.
고급 참고 — μPD765 계열에서 N=0과 DTL

Sector ID의 기본 크기 해석은 128 × 2^N입니다. 다만 μPD765 계열의 일부 READ/WRITE 명령에서는 N=0일 때 명령 parameter인 DTL(Data Length)이 실제 전송 길이에 관여할 수 있습니다. 따라서 기본식과 특정 FDC 명령의 전송 규칙을 같은 것으로 확대하지 않습니다.

디스크 종류와 배치

7. 플로피 종류 이름만 보고 Track 수와 Sector 수까지 모두 같다고 생각하면 안 된다

겉으로 같은 종류로 부르는 플로피라도 실제로 몇 개의 둥근 기록 줄이 있고, 한 줄을 몇 구간으로 나누었는지는 포맷에 따라 달라질 수 있습니다. 특히 게임 디스크는 일반적인 배치와 다른 번호나 배치를 사용할 수도 있습니다.

이제 이름을 붙이면: 2D / 2DD / 2HD는 매체와 기록 밀도 계열을 구분하는 이름이고, 실제 Track 수·Side 수·Sector 수·Sector 크기 같은 배치를 묶어서 Geometry라고 설명합니다. 두 개념을 같은 뜻으로 외우지 않습니다.

디스크 읽기 전체 과정

8. CPU가 “읽어라”라고 요청하면 디스크 제어 장치가 위치를 맞추고 목표 Sector를 찾아 데이터를 읽는다

CPU가 플로피의 자기 신호를 직접 하나씩 읽는 것은 아닙니다. 디스크 읽기를 맡은 제어 장치가 읽기/쓰기 장치를 필요한 위치로 옮기고, 원판이 돌아오기를 기다리고, 지나가는 Sector의 식별값을 확인한 뒤 실제 데이터를 전송합니다.

이제 이름을 붙이면: 이런 디스크 제어 장치를 FDC(Floppy Disk Controller)라고 합니다. 앞에서 배운 SEEK, 회전 대기, C/H/R/N 비교가 FDC의 읽기 과정에서 하나로 연결됩니다.
PC-88에서 실제로 만나는 이름 — μPD765 / μPD765A

PC-88의 대표적인 5.25인치 디스크 서브시스템에서는 NEC의 μPD765/μPD765A 계열 FDC를 만납니다. 따라서 실제 게임 분석에서 SEEK, READ DATA, READ ID, C/H/R/N 같은 이름이 나오면 이 FDC가 수행하는 디스크 작업과 연결해서 생각할 수 있습니다. ST0/ST1/ST2는 명령 실행 뒤 FDC가 돌려주는 상태 정보로, 정상 완료 여부나 오류 원인을 판정할 때 사용합니다.

다만 FDC라는 일반 개념과 μPD765라는 특정 칩 이름은 같은 말이 아닙니다. 또한 초기 외장 지능형 디스크 장치와 후속 내장형 모델은 물리적 구성 방식이 다를 수 있습니다.

1. 목표 기록 줄로 이동필요하면 SEEK로 Head를 목표 Track/Cylinder 위치까지 이동
↓
2. 원하는 Sector가 올 때까지 기다림원판이 회전하면서 ID Field가 Head 아래로 지나감
↓
3. C/H/R/N 비교요청한 ID와 지금 읽은 ID가 모두 맞는지 확인
↓

앞의 내용과 연결: 2장은 1번의 위치 이동, Lab 1은 2번의 회전, Lab 4는 3번의 ID 비교를 보여 줬습니다. 여기서는 이 동작들이 실제 FDC의 읽기 과정에서 이어진다는 것을 정리합니다.

9. PC-88에서는 메인 CPU가 디스크 장치를 혼자 직접 다루지 않고, 디스크 일을 맡은 별도 쪽에 요청한다

게임을 실행하는 주 CPU가 모든 디스크 동작을 직접 처리한다고 생각하면 실제 코드를 따라가다가 막힐 수 있습니다. PC-88의 대표적인 디스크 구조에서는 디스크 작업을 맡은 별도의 처리 쪽이 있고, 주 CPU는 그쪽에 요청을 보내 결과를 받습니다.

플로피를 파일로 보관하기

11. 실제 플로피를 컴퓨터 파일 하나로 보관하려면 데이터뿐 아니라 “어디에 있던 데이터인지” 정보도 함께 저장해야 한다

실제 플로피에는 여러 둥근 기록 줄과 여러 데이터 구간이 있습니다. 이를 PC 파일 하나로 옮길 때 실제 데이터 바이트만 이어 붙이면 각 데이터가 원래 어느 줄의 어느 구간이었는지 알기 어렵습니다. 그래서 위치와 상태를 설명하는 정보도 함께 파일 안에 기록합니다.

이제 이름을 붙이면: 이런 방식으로 PC-88 계열 플로피의 논리 구조를 보존하는 대표적인 디스크 이미지 형식이 D88입니다. D88은 실제 자기 신호 전체를 그대로 복사한 것이 아니라 Track/Sector 정보와 payload, 일부 상태를 파일 구조로 표현합니다.

실제 Floppy

회전, 자기 신호, 실제 gap, timing, 물리적 angular 위치가 존재합니다.

D88 File

Disk Header, Track Offset Table, Sector Header, Sector Payload로 track/sector와 일부 상태 정보를 표현합니다.

D88 = 실물의 완전한 bit-for-bit 자기 복제는 아닙니다. 정확한 flux와 모든 gap/timing 정보를 그대로 저장하는 raw flux 형식과는 성격이 다릅니다.
파일 안의 위치표

12. D88 파일 앞부분에는 “각 Track 데이터가 파일의 어디에서 시작하는지” 알려 주는 위치표가 있다

D88 안에 여러 Track의 데이터가 이어져 있다면 원하는 Track을 찾으려고 파일 처음부터 전부 훑을 필요가 없습니다. 파일 앞부분에 “첫 번째 Track은 몇 번째 바이트부터, 다음 Track은 몇 번째 바이트부터”처럼 각 Track의 시작 위치를 적어 둔 표가 있습니다.

14. D88에서는 현재 Sector Header와 실제 Data 길이를 더하면 다음 Sector block의 시작을 계산할 수 있다

D88에서 한 Sector는 앞의 16바이트 설명 정보와 그 뒤의 실제 데이터로 저장됩니다. 따라서 현재 Sector가 파일 어디에서 시작하는지와 실제 데이터 길이를 알면, 두 길이를 더해서 바로 다음 Sector가 시작하는 위치를 계산할 수 있습니다.

이제 이름을 붙이면: Sector Header + Payload를 하나의 Sector block으로 보고 파일 안에서 다음 block으로 이동하는 과정을 이 강좌에서는 Sector Walker라고 부릅니다.

실제 게임 데이터 바이트가 똑같아도 어떤 파일은 데이터만 차례대로 붙여 놓고, 어떤 파일은 각 데이터 앞에 위치와 상태를 설명하는 정보를 함께 넣습니다. 또 파일 시스템을 쓰는 경우에는 여러 Sector를 묶어 하나의 파일로 관리할 수도 있습니다.

이제 이름을 붙이면: 이 강좌에서는 Sector payload만 선형으로 이어 놓은 학습용 표현을 RAW라고 부르고, metadata까지 함께 가진 형식을 D88이라고 구분합니다. 운영체제가 여러 Sector를 파일 단위로 묶어 관리하는 층은 File system입니다. 여기서 RAW는 구조 비교를 위해 payload만 선형으로 이어 놓은 학습용 표현이며, 모든 .raw 파일 형식을 이렇게 정의하는 것은 아닙니다.

18. 16칸 × 16칸짜리 흑백 글자 그림은 한 줄에 2바이트, 전체 32바이트로 저장할 수 있다

이제 이름을 붙이면: 이렇게 글자 하나를 점 배열로 표현한 데이터를 16×16 Glyph라고 부릅니다. 한 줄은 raster라고도 하며, Kanji ROM에서는 한 raster마다 왼쪽 8dot와 오른쪽 8dot를 읽습니다.
한 row = 왼쪽 8dot 1byte + 오른쪽 8dot 1byte → 2byte × 16 rows = 32byte

20. JIS 값의 특정 비트를 재배열해서 Kanji ROM 회로가 사용하는 위치값을 만든다

JIS는 문자 번호이고 Kanji ROM 회로는 별도의 주소 배치를 사용합니다. 따라서 JIS 값을 그대로 ROM 주소로 쓰는 것이 아니라, 문자 영역에 맞는 규칙으로 특정 비트들을 골라 다시 배치해야 합니다.

이제 이름을 붙이면: PC-8801 Kanji ROM 회로에 지정하는 위치값을 이 강좌에서는 KANJI access라고 부릅니다. 비한자 영역과 제1수준 한자 영역은 주소 배치 규칙이 서로 다릅니다.
JIS 21xx~27xx — 기호·가나 등 비한자A = ((J & 001Fh) << 4)
| ((J & 0060h) << 7)
| ((J & 0700h) << 1)
JIS 30xx~4Fxx — 제1수준 한자A = ((J & 001Fh) << 4)
| ((J & 0060h) << 9)
| ((J & 1F00h) << 1)

Lab 8 — 제1수준 한자 JIS가 KANJI access로 바뀌는 계산 보기

먼저 제1수준 한자 예제로 한 식의 비트 재배열을 단계별로 확인합니다. 비한자 영역은 아래 별도 예에서 다른 식을 사용합니다.

계산된 KANJI access에서 16줄이 이어지는 범위

여기서는 아직 ROM dump 파일의 byte offset을 계산하지 않습니다. 현재는 한 glyph의 16개 raster가 KANJI access에서 어떻게 연속되는지만 봅니다.

비한자 영역 예 — JIS 2421h
(2421h & 001Fh) << 4 = 0010h
(2421h & 0060h) << 7 = 1000h
(2421h & 0700h) << 1 = 0800h

0010h | 1000h | 0800h = 1810h
제1수준 한자 예 — JIS 3441h
(3441h & 001Fh) << 4 = 0010h
(3441h & 0060h) << 9 = 8000h
(3441h & 1F00h) << 1 = 2800h

0010h | 8000h | 2800h = A810h
영역을 먼저 확인: 2421h → 1810h와 3441h → A810h는 서로 다른 JIS 영역의 주소 배치 예입니다. 하나의 식을 모든 JIS 값에 적용하지 않습니다. 제2수준 한자 영역은 이 절에서 섞지 않습니다.

이 Lab의 목적: 3부의 최종 목표는 계산식을 많이 외우는 것이 아니라, 먼저 “지금 보고 있는 값이 어느 좌표계에 속하는가”를 틀리지 않고 판단하는 것입니다.
확인 문제

3부 확인 문제

1. 원판이 회전할 때 Head도 원판과 함께 둘레를 도는가?
아니다. 원판이 회전하고 Head는 선택된 반지름 위치에 머문다. Track을 바꿀 때 Head가 안쪽/바깥쪽으로 이동한다.
2. SEEK가 끝났다는 것은 Sector Data까지 읽었다는 뜻인가?
아니다. SEEK는 Head를 원하는 Track 위치로 이동시키는 단계다. 이후 회전 대기와 ID 비교가 필요하다.
3. Side와 Head는 같은 뜻인가?
아니다. Side는 디스크의 면이고 Head는 그 면을 읽고 쓰는 물리 장치다.
4. 실제 Track/Head 위치와 Sector ID의 C/H는 항상 같은 뜻인가?
아니다. C/H는 Sector ID Field에 기록된 값이다. 정상 포맷에서는 실제 Track/Head 위치와 자연스럽게 대응하는 경우가 많지만 개념적으로는 별도이며 특수 포맷에서는 다를 수 있다.
5. R=02이면 D88에서 반드시 두 번째 Sector Block인가?
아니다. R은 Sector ID의 Record 값이고 D88 block 순서와는 별개다.
6. N=1의 nominal Sector Data 크기는?
128×2¹ = 256byte.
7. D88 Track Offset은 실제 원판의 CHRN인가?
아니다. D88 파일 시작점을 기준으로 Track Block이 시작하는 file offset이다.
8. D88 file offset 9000h이면 RAM 9000h으로 자동 대응하는가?
아니다. Loader가 어떤 Sector를 어느 RAM 주소에 읽는지 실행을 추적해야 한다.
9. Kanji ROM이 Glyph를 직접 화면에 그리는가?
아니다. Kanji ROM은 Glyph byte를 제공하고 프로그램의 문자 출력 루틴이 그 데이터를 이용해 화면에 그린다.
10. 16×16 흑백 Glyph가 32byte인 이유는?
한 row가 16pixel = 2byte이고 16row이므로 2×16=32byte다.
11. JIS 3441h와 KANJI access A810h은 같은 좌표인가?
아니다. JIS의 특정 bit를 재배열해 하드웨어 access를 만든다.
12. KANJI access와 ROM dump byte offset은 같은가?
아니다. 이 강좌에서 다루는 dump 표현에서는 한 access가 좌/우 두 byte에 대응하므로 byte offset은 access×2다.
13. Shift-JIS 계열 token이 모든 PC-88 게임의 보편적 내부 문자 형식인가?
아니다. 게임마다 내부 표현이 다를 수 있으며 실제 코드로 확인해야 한다.
14. 화면에 일본어가 보인다는 사실만으로 시스템 Kanji ROM 사용을 확정할 수 있는가?
아니다. 게임 자체 Font를 사용할 수도 있으므로 실제 I/O와 Font Data 경로를 확인해야 한다.
