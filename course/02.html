2부의 가장 중요한 원칙: 어셈블리 코드를 한국어 문장으로 한 줄씩 번역하는 것만으로는 역분석이 되지 않습니다. 먼저 각 명령이 무엇을 읽고, 무엇을 바꾸고, 다음에 어디로 실행을 이어가는지를 추적한 뒤, 여러 줄을 묶어 “이 코드 블록이 무슨 일을 하는가?”를 판단해야 합니다.

처음에는 이렇게 읽고

LD E,(HL)          ; HL이 가리키는 메모리의 1byte를 E로 읽음
INC HL             ; HL을 1 증가시켜 다음 byte를 가리킴
LD A,E             ; E의 값을 A로 복사
AND 0Fh            ; A의 하위 4bit만 남김
CP 01h             ; A가 01h인지 비교
JP Z,0452h         ; 같으면 0452h로 이동

마지막에는 이렇게 보이는 코드도 읽는다

02ED  5E        LD E,(HL)
02EE  23        INC HL
02EF  7B        LD A,E
02F0  32 84 0C  LD (0C84h),A
02F3  E6 0F     AND 0Fh
02F5  FE 01     CP 01h
02F7  CA 52 04  JP Z,0452h

주소와 machine code byte, assembly만 보이는 상태에서도 register와 memory의 변화를 따라가고, 마지막에는 이 코드가 stream에서 값을 하나 읽어 분류하는 형태라는 식으로 한 단계 높은 해석을 할 수 있게 되는 것이 목표입니다.

문법

1. Z80 코드를 읽기 위한 표기법

1-1. 어셈블리 한 줄은 무엇으로 이루어지는가

처음 Z80 코드를 보면 영어 약자와 괄호, 쉼표, 숫자가 섞여 있어 한 줄 전체가 하나의 암호처럼 보일 수 있습니다. 그러나 한 줄을 구성하는 요소는 몇 가지로 나눌 수 있습니다.

LOOP:
    LD A,(HL)      ; HL이 가리키는 byte를 A로 읽음
    INC HL         ; 다음 주소로 이동
    JR NZ,LOOP     ; Z flag가 0이면 LOOP로 돌아감
LOOP:
label입니다. 사람이 위치에 이름을 붙인 것입니다.
LD / INC / JR
mnemonic입니다. CPU instruction을 사람이 읽을 수 있게 적은 이름입니다.
A, (HL), HL
operand입니다. 명령이 사용할 register, 값, 주소 등을 나타냅니다.
,
여러 operand를 구분합니다.
;
이 뒤는 comment입니다. CPU가 실행하지 않으며 사람이 이해하기 위해 적습니다.
헷갈리지 말 것: LOOP라는 글자가 게임 ROM이나 RAM의 machine code 안에 그대로 들어 있는 것이 아닙니다. assembler는 label을 실제 주소나 상대 이동값으로 바꿉니다. 반대로 disassembler가 자동으로 보여주는 이름도 사람이 이해하기 쉽게 붙인 이름일 수 있습니다.

1-2. 두 operand 명령은 보통 ‘목적지, 원본’ 순서로 읽는다

Z80의 LD처럼 두 operand를 쓰는 명령은 처음에 왼쪽이 목적지, 오른쪽이 원본이라는 방향을 익히면 읽기 쉽습니다.

LD A,B             ; B → A
LD (HL),A          ; A → HL이 가리키는 메모리
LD HL,9000h        ; 9000h → HL
LD destination, source

LD A,B는 “A를 B에 넣는다”가 아니라 B의 값을 A로 복사한다고 읽습니다. 다만 모든 Z80 instruction을 억지로 이 공식에 맞추면 안 됩니다. CP, JR, PUSH처럼 operand의 의미가 전혀 다른 명령도 있습니다.

1-3. Z80 설명서의 n, nn, r, d, e, b, cc와 register-pair 기호

Z80 CPU manual이나 instruction table에는 실제 숫자와 register 이름 대신 n, nn, r, d 같은 기호가 나옵니다. 이 기호들은 CPU가 실행하는 문자가 아니라 여러 실제 instruction을 한 줄로 나타내기 위한 자리표시자입니다.

예를 먼저 봅시다.
LD r,n은 완성된 instruction 하나가 아닙니다. r=B, n=3Ch를 대입하면 실제 instruction LD B,3Ch가 됩니다.

설명서의 일반형 → 실제 operand 대입 → 실제 assembly라는 순서로 읽으면 됩니다.

먼저 용어 두 개: 즉시값과 displacement

즉시값(immediate value)

명령 안에 값 자체가 직접 들어 있는 경우입니다.

LD A,05h           ; 05h라는 값 자체를 A에 넣음

여기서 05h를 다른 RAM 위치에서 읽어 오는 것이 아닙니다.

displacement

기준 위치에서 얼마나 앞이나 뒤로 떨어졌는지 나타내는 이동량입니다.

IX = 9000h
+5  → 9005h
-2  → 8FFEh

signed라고 적혀 있으면 +와 -를 모두 표현하는 값으로 해석합니다.

먼저 자주 만나는 기본 기호

표기Zilog 설명서에서의 뜻실제 예
r8bit register A, B, C, D, E, H, L 중 하나LD r,n → LD B,3Ch
n0~255 범위의 1byte unsigned 값n=3Ch
nn0~65535 범위의 2byte unsigned 값nn=9000h
dIX/IY indexed addressing에 쓰이는 -128~+127 범위의 1byte signed displacement(IX+05h), (IY-02h)
bbit 번호 0~7BIT b,r → BIT 7,A
eZilog 표에서 현재 instruction 위치를 기준으로 표시하는 JR 목적지의 상대 offset. 범위 -126~+129JR e
cc조건 코드: NZ, Z, NC, C, PO, PE, P, M 중 하나JP cc,nn → JP Z,9000h
e와 실제 JR operand의 차이
e를 “기계어에 그대로 저장되는 signed 8bit displacement”라고 이해하면 정확하지 않습니다. Zilog의 notation table에서 e는 현재 instruction 위치 기준 상대 offset이라 -126~+129로 적혀 있습니다. 반면 JR 기계어의 실제 operand byte는 JR 다음 PC 기준 signed 8bit displacement이며 -128~+127입니다. 아래에서 숫자로 직접 비교합니다.

n — 1byte 값 하나가 들어가는 자리

LD r,n             ; 설명서의 일반형
LD B,3Ch           ; r=B, n=3Ch를 대입한 실제 instruction
LD r,n → r=B, n=3Ch → LD B,3Ch
06 3C
│  └─ n = 3Ch
└──── opcode: LD B,n

즉 설명서의 추상 표기 LD r,n이 실제 assembly LD B,3Ch가 되고, 다시 CPU가 읽는 machine code 06 3C로 이어집니다.

n은 문자 n 하나를 프로그램에 적으라는 뜻이 아닙니다. 한 byte짜리 unsigned 값이 들어가는 자리라는 뜻입니다.

잘못된 이해: “n이 한 글자라서 8bit다.”
정확한 이해: Zilog가 1byte unsigned operand를 나타내기 위해 기호 n을 사용하기로 정한 것입니다.

nn — 2byte 값 하나가 들어가는 자리

LD dd,nn           ; Zilog 상세 16bit Load 설명의 일반형
LD HL,9000h        ; dd=HL, nn=9000h

여기서 dd는 BC/DE/HL/SP 중 하나를 뜻하며 아래 register-pair 절에서 다시 정확히 정리합니다. nn은 “n 두 개”라는 뜻이 아니라 16bit 값 하나를 뜻합니다. 같은 9000h라도 instruction에 따라 역할이 달라집니다.

LD HL,9000h        ; 9000h라는 16bit 값을 HL에 넣음
JP 9000h           ; 9000h를 다음 실행 주소로 사용
nn = 주소라고 외우면 안 됩니다. nn은 16bit 값 자리입니다. 그 값을 주소로 사용할지 단순 숫자로 사용할지는 instruction의 의미가 결정합니다.

나중에 machine code까지 연결하면 LD HL,9000h은 다음처럼 보입니다.

21 00 90
│  └──┘
│   nn = 9000h
└─ opcode

16bit 값 9000h가 operand byte에서는 00 90 순서로 놓이는 이유는 Z80의 little-endian 저장 순서 때문입니다.

r — 설명서 기호에 실제 register를 대입한다

LD r,n             ; 설명서
   │ │
   │ └─ n = 3Ch
   └─── r = B

        ↓

LD B,3Ch           ; 실제 instruction

Zilog의 기본 notation에서 r은 A, B, C, D, E, H, L 중 하나입니다.

INC r              ; 일반형
INC A              ; r=A
INC B              ; r=B
INC C              ; r=C

d — IX/IY의 기준 주소에 더하는 실제 signed 8bit displacement

d는 실제로 -128~+127 범위의 signed 8bit 값입니다.

LD A,(IX+d)        ; 설명서의 일반형

IX=9000h, d=+05h라면:

LD A,(IX+05h)      ; RAM[9005h]의 1byte를 A로 읽음
9000h + 0005h = 9005h

이번에는 d=-2라면:

LD A,(IX-02h)      ; RAM[8FFEh]의 1byte를 A로 읽음
9000h - 0002h = 8FFEh

즉 d는 메모리의 effective address를 계산할 때 IX/IY에 더해지는 값입니다.

e — Zilog 설명서의 e와 JR 기계어 displacement를 구분한다

여기가 d와 가장 쉽게 섞이는 부분입니다. 둘 다 상대값이지만 무엇을 기준으로 무엇을 계산하는지가 다릅니다.

d

LD A,(IX+05h)

IX + d로 메모리 주소를 계산합니다.

JR의 상대값

JR SKIP

실행 흐름의 다음 PC를 계산합니다.

예를 들어 JR instruction 시작 주소가 8000h이고 목적지가 8008h라고 합시다.

8000h : 18 06      JR 8008h
8002h : ...
8008h : ...         ; 목적지
Zilog notation의 현재 위치 기준 offset e는 8008h-8000h = +8입니다.
JR instruction 길이는 2byte이므로 instruction을 읽은 뒤 PC는 8002h입니다.
기계어에 실제 저장되는 displacement byte는 8008h-8002h = +6입니다.
그래서 machine code가 18 06이 됩니다. 18은 JR opcode, 06은 실제 signed displacement입니다.
Zilog 표의 e = +8 / 실제 encoded displacement = +6

최대·최소 범위도 이 2byte 차이 때문에 다릅니다.

구분기준점범위
Zilog notation의 e현재 JR instruction 시작 위치-126 ~ +129
기계어 displacement byteJR 2byte를 읽고 난 뒤의 PC-128 ~ +127
실제 source에서는 보통 직접 +6을 적을 필요가 없습니다. JR SKIP처럼 label을 쓰면 assembler가 목적지와 현재 주소를 계산해 실제 displacement byte를 만들어 줍니다. 역분석할 때는 반대로 machine byte를 보고 목적지를 계산하게 됩니다.

b — BIT/SET/RES에서 어느 bit를 말하는가

BIT b,r            ; 설명서의 일반형
BIT 7,A            ; b=7, r=A → A의 bit 7 검사

SET b,r            ; 일반형
SET 3,B            ; b=3, r=B → B의 bit 3을 1로

RES b,r            ; 일반형
RES 0,C            ; b=0, r=C → C의 bit 0을 0으로

b는 0~7 사이의 bit 번호입니다. 8bit 값의 최상위가 bit 7, 최하위가 bit 0입니다.

cc — 조건 자체가 들어가는 자리

cc는 조건부 JP/CALL/RET 등에 들어가는 condition code입니다.

cc검사하는 상태
NZZ=0
ZZ=1
NCC=0
CC=1
POP/V=0
PEP/V=1
PS=0
MS=1
JP cc,nn           ; 설명서의 일반형
JP Z,9000h         ; cc=Z, nn=9000h
JP NZ,8000h        ; cc=NZ, nn=8000h
P와 M을 단순히 “signed 크기 비교 결과”라고 외우면 안 됩니다. P/M은 S flag가 0인지 1인지를 검사합니다. signed 대소 비교는 overflow까지 고려해야 하므로 CP 뒤에서 S만 보는 것으로 항상 해결되지 않습니다.

register pair 기호는 하나가 아니다

16bit register를 나타내는 설명서 기호를 전부 rr이라고 뭉뚱그리면 실제 Zilog manual을 읽을 때 틀리게 됩니다. instruction마다 허용되는 register pair 집합이 달라서 서로 다른 기호를 사용합니다.

기호들어갈 수 있는 register pair실제 manual 예
qqBC, DE, HL, AFPUSH qq, POP qq
ssBC, DE, HL, SPADD HL,ss, INC ss
ppBC, DE, IX, SPADD IX,pp
rrBC, DE, IY, SPADD IY,rr
ddBC, DE, HL, SPLD dd,nn — Zilog의 상세 16bit LD 설명에서 사용
왜 qq/ss/pp/rr가 따로 있는가? 예를 들어 PUSH qq에서는 AF가 가능한 반면 SP는 그 자리에 들어가지 않습니다. 반대로 ADD HL,ss에서는 SP가 가능하지만 AF는 들어가지 않습니다. 따라서 “16bit register 아무거나”라고 한 기호로 쓰면 허용 operand를 표현할 수 없습니다.
PUSH qq            ; qq = BC, DE, HL, AF
PUSH AF            ; 가능

ADD HL,ss          ; ss = BC, DE, HL, SP
ADD HL,SP          ; 가능

ADD IX,pp          ; pp = BC, DE, IX, SP
ADD IX,IX          ; 가능

ADD IY,rr          ; rr = BC, DE, IY, SP
ADD IY,IY          ; 가능
Zilog manual을 읽을 때 주의: 공식 2016 Instruction Notation Summary에는 qq/ss/pp/rr가 정리되어 있고, 상세 16bit Load instruction 페이지에서는 dd라는 표기도 추가로 사용됩니다. 따라서 기호 하나만 외우지 말고 그 instruction에서 그 기호가 어떤 register 집합을 뜻하는지 확인해야 합니다.

s와 m도 instruction table에서 만날 수 있다

기호정확한 의미
sr, n, (HL), (IX+d), (IY+d) 중 하나
mr, (HL), (IX+d), (IY+d) 중 하나. n은 포함하지 않음

여기서도 핵심은 문자를 외우는 것이 아니라 그 기호가 실제로 어떤 operand 후보를 대표하는지 펼쳐 볼 수 있는 것입니다.

설명서 한 줄을 실제 코드로 바꾸는 사고 순서

LD r,n
→ r은 A/B/C/D/E/H/L 중 하나
→ n은 00h~FFh의 1byte 값
→ r=B, n=3Ch를 선택
→ LD B,3Ch

JP cc,nn
→ cc는 조건 코드 중 하나
→ nn은 16bit 값
→ cc=Z, nn=9000h
→ JP Z,9000h
확인 문제 — 설명서 표기를 실제 코드로 바꿔 보자

문제 1. LD r,n에서 r=C, n=20h라면?

답: LD C,20h

문제 2. BIT b,r에서 b=7, r=A라면?

답: BIT 7,A

문제 3. JP cc,nn에서 cc=NZ, nn=4000h라면?

답: JP NZ,4000h

문제 4. IX=9000h일 때 LD A,(IX-02h)가 읽는 주소는?

답: 8FFEh입니다.

문제 5. 8000h의 JR이 8008h로 이동한다면 Zilog notation의 현재 위치 기준 e와 실제 machine displacement는?

답: e는 +8, 실제 JR 다음 PC(8002h) 기준 displacement byte는 +6입니다.

문제 6. PUSH qq에서 qq에 SP가 들어갈 수 있는가?

답: 없습니다. qq는 BC, DE, HL, AF입니다. SP가 포함되는 다른 register-pair 기호와 구별해야 합니다.

1-4. CPU instruction과 assembler directive는 다르다

ORG 8000h          ; assembler에게 배치 기준 주소를 지정
DB 41h,42h,43h     ; byte 데이터를 배치
DW 9000h           ; word 데이터를 배치

LD A,05h           ; 실제 Z80 instruction
RET                ; 실제 Z80 instruction

LD와 RET은 Z80 CPU가 실행할 machine instruction으로 변환됩니다. 반면 ORG, DB, DW 같은 것은 assembler에게 파일을 어떻게 만들지 지시하는 directive(의사 명령)입니다. CPU가 DB라는 명령을 실행하는 것이 아닙니다.

source와 disassembly의 차이: 사람이 작성한 source에는 label, comment, directive가 풍부할 수 있습니다. 게임을 역분석할 때 처음 보는 disassembly에는 대개 주소, byte, instruction만 있고 “이 루틴은 문자 출력” 같은 설명은 없습니다. 그 의미를 찾아가는 것이 역분석입니다.

1-5. 잘못 읽기 쉬운 첫 번째 예

잘못된 해석

LD A,B             ; A를 B로 보낸다?

operand의 방향을 반대로 읽은 것입니다.

2-1. 괄호가 있느냐 없느냐는 완전히 다른 뜻이다

Z80 코드를 읽을 때 가장 중요한 구분 중 하나가 값 자체와 그 값이 가리키는 메모리의 내용입니다.

핵심: 괄호는 “이 숫자를 한 번 더 계산한다”는 장식이 아닙니다. Z80 assembly에서 괄호는 해당 operand가 메모리 접근임을 나타내는 데 사용됩니다.

2-2. LD HL,9000h와 LD HL,(9000h)는 무엇이 다른가

즉시값

LD HL,9000h        ; 숫자 9000h를 HL에 넣음

실행 후 HL=9000h입니다. RAM 9000h의 내용은 읽지 않았습니다.

메모리에서 16bit 읽기

LD HL,(9000h)      ; 9000h부터 저장된 16bit 값을 HL로 읽음

RAM 9000h와 9001h의 두 byte를 읽어 HL을 만듭니다.

예를 들어 메모리가 다음과 같다고 합시다.

9000h
34h
9001h
12h
LD HL,(9000h)      ; low byte 34h, high byte 12h를 읽음
HL = 1234h

Z80은 이런 16bit 값을 메모리에 놓을 때 낮은 byte를 낮은 주소에 두는 little-endian 방식을 사용합니다. 0부에서 배운 내용이 실제 instruction에 그대로 연결됩니다.

2-3. instruction마다 byte 길이가 다르다

8000h : 21 00 90    LD HL,9000h      ; 3 bytes
8003h : 3E 05       LD A,05h         ; 2 bytes
8005h : 77          LD (HL),A        ; 1 byte

CPU가 첫 번째 instruction을 실행하고 나면 다음 instruction은 8001h가 아니라 8003h에서 시작합니다. 첫 instruction이 opcode 1byte와 operand 2byte, 총 3byte이기 때문입니다.

초보자가 자주 하는 착각: “instruction 하나 실행 = PC가 1 증가”가 아닙니다. PC는 instruction을 구성하는 byte를 fetch하면서 다음 위치로 진행합니다. instruction의 길이가 다르므로 다음 instruction 주소도 달라집니다.

2-4. opcode와 operand byte를 직접 본다

210090→LD HL,9000h

21h은 이 경우 LD HL,nn을 뜻하는 opcode이고, 00 90은 16bit operand 9000h가 little-endian으로 저장된 것입니다.

중요: hex dump의 아무 위치에서나 disassemble하면 안 됩니다. code의 instruction 경계를 잘못 잡으면 원래 데이터나 operand byte를 opcode라고 해석해 전혀 다른 instruction이 나온 것처럼 보일 수 있습니다.

직접 실행: PC가 instruction 길이만큼 이동하는 모습

아래 세 instruction을 한 번씩 실행해 보세요. 한 줄 실행할 때마다 PC가 무조건 1 증가하는 것이 아니라, 그 instruction의 byte 길이만큼 다음 위치로 이동합니다.

8000h: 21 00 90    LD HL,9000h     ; 3byte
8003h: 3E 05       LD A,05h        ; 2byte
8005h: 77          LD (HL),A       ; 1byte
PC=8000h HL=0000h A=00h RAM[9000h]=00h 다음 실행: 21 00 90 LD HL,9000h

2-5. 8bit와 16bit는 범위를 넘으면 다시 돌아온다

LD A,FFh           ; A = FFh
INC A              ; FFh + 1 → 00h

LD HL,FFFFh        ; HL = FFFFh
INC HL             ; FFFFh + 1 → 0000h

8bit register는 256가지 bit pattern만, 16bit register는 65,536가지 pattern만 담을 수 있습니다. 범위를 넘어간 추가 bit는 register에 남지 않으므로 값이 처음으로 돌아오는 것처럼 보입니다. 이것을 wrap-around라고 생각하면 이해하기 쉽습니다.

4. 산술·논리 명령은 게임 코드에서 무엇을 계산하는가

4-1. INC와 DEC — 단순한 +1/-1이 아니다

INC A              ; A를 1 증가
DEC B              ; B를 1 감소
INC HL             ; HL 전체 16bit 값을 1 증가
DEC DE             ; DE 전체 16bit 값을 1 감소

INC HL은 HL이 가리키는 메모리를 바꾸는 명령이 아닙니다. HL register 자체를 증가시킵니다. 반대로 메모리 byte를 증가시키려면 INC (HL)처럼 메모리 operand를 사용해야 합니다.

INC HL

HL = 9000h
INC HL             ; HL = 9001h

주소 pointer를 다음 byte로 이동시키는 데 자주 보입니다.

INC (HL)

HL = 9000h
RAM[9000h] = 05h
INC (HL)           ; RAM[9000h] = 06h

HL은 그대로이고 메모리의 byte가 증가합니다.

직접 실행: register를 증가시키는 것과 메모리를 증가시키는 것

각 버튼은 같은 초기 상태 HL=9000h, RAM[9000h]=05h에서 해당 instruction 하나만 실행합니다. 따라서 두 명령의 차이를 바로 비교할 수 있습니다.

HL=9000h RAM[9000h]=05h 아직 실행하지 않았습니다.

4-2. 8bit INC와 16bit INC는 flag 동작도 다르다

INC A 같은 8bit INC는 S, Z, H, P/V, N 등의 상태에 영향을 주지만 Carry flag는 보존합니다. 반면 INC HL 같은 16bit register-pair INC는 이 일반 flag들을 바꾸지 않습니다.

왜 알아야 하나: 조건 분기 직전에 INC HL이 있다고 해서 “Z flag가 HL의 결과에 맞춰 바뀌었겠지”라고 생각하면 안 됩니다. 어떤 instruction이 어떤 flag를 바꾸는지 확인해야 합니다.

4-3. ADD / SUB는 주소 계산에도 사용된다

LD HL,9000h        ; 기준 주소
LD DE,0020h        ; 이동량 32byte
ADD HL,DE          ; HL = 9020h

게임 역분석에서 산술 명령은 점수나 HP 계산에만 나오지 않습니다. table의 다음 항목, 화면의 다음 행, 구조체의 다음 필드처럼 주소를 계산하는 코드에서도 매우 자주 보입니다.

9000h + 0020h = 9020h

ADC와 SBC는 Carry까지 계산에 포함합니다. 여러 byte에 걸친 큰 숫자를 계산하거나 이전 연산의 자리올림/빌림을 이어받을 때 사용됩니다. 처음에는 “ADD/SUB에 Carry를 포함한 형태”라고 이해하면 충분합니다.

4-4. AND — 필요한 bit만 남기는 mask

LD A,B6h           ; A = 1011 0110
AND 0Fh            ;     0000 1111 과 AND
                    ; 결과 0000 0110 = 06h
B6h AND 0Fh = 06h

0Fh는 이 예에서 하위 4bit를 남기고 상위 4bit를 0으로 만드는 mask입니다. control byte의 일부 bit만 command 번호로 쓰는 코드에서 이런 형태를 자주 볼 수 있습니다.

4-5. OR — 특정 bit를 켜고, XOR — bit를 뒤집는다

OR 80h             ; bit 7을 1로 만드는 데 사용할 수 있음
XOR 01h            ; bit 0을 뒤집는 데 사용할 수 있음
XOR A              ; A XOR A = 0이므로 A를 00h로 만듦
자주 보는 Z80 관용 패턴: XOR A는 A에 어떤 값이 들어 있든 A와 자기 자신을 XOR하므로 결과가 0이 됩니다. 그래서 A를 0으로 만드는 짧고 흔한 코드로 사용됩니다.

4-6. BIT / SET / RES는 한 byte의 특정 bit만 다룬다

BIT 7,A            ; A의 bit 7 검사. bit가 0이면 Z=1, 1이면 Z=0
SET 3,A            ; A의 bit 3을 1로 만듦
RES 2,A            ; A의 bit 2를 0으로 만듦

BIT는 검사 대상의 값을 바꾸지 않습니다. 공식 flag 동작에서 H=1, N=0, C는 보존되며, Z는 검사한 bit가 0일 때 1이 됩니다. PC-88의 I/O register처럼 한 byte 안에서 각 bit가 서로 다른 hardware 상태를 나타내는 경우 특히 중요합니다. byte 전체를 바꾸는 대신 필요한 bit 하나만 검사하거나 조작할 수 있습니다.

5-1. F register 전체를 먼저 정확히 본다

5-2. bit 5와 bit 3 — 공식적으로 Not Used지만 실제 Z80에서는 변한다

Zilog 공식 문서에서는 F의 bit 5와 bit 3을 X / Not Used로 취급합니다. 하지만 실제 Z80 silicon에서는 이 두 bit도 여러 instruction의 실행 결과에 따라 값이 변합니다. 비공식 문헌과 emulator 구현에서는 보통 F5/F3, 또는 Y/X flag라고 부릅니다.

두 가지를 동시에 기억해야 합니다.
① 공식 프로그래밍 사양: bit 5와 3은 사용하지 않는 bit입니다.
② 실제 CPU 동작: 두 bit의 값이 여러 instruction에서 일정한 규칙으로 변하며, 일부 프로그램은 그 동작에 의존하기도 합니다.
고급 참고 — F5/F3의 실제 값 출처와 예외

일반적인 결과형 instruction에서는 결과 bit가 반영되는 경우가 많다

예: 어떤 8bit 연산 결과가 28h라고 가정

28h = 0010 1000b
       │   │
       │   └─ bit 3 = 1 → F3가 1이 되는 계열이 많음
       └───── bit 5 = 1 → F5가 1이 되는 계열이 많음

그러나 이것을 “F5/F3는 언제나 결과의 bit 5/3 복사본”이라는 만능 규칙으로 외우면 틀립니다. 실제로 명령별 예외가 있습니다.

CP는 대표적인 예외다 — F5/F3가 subtraction 결과가 아니라 operand에서 온다

LD A,40h           ; A = 40h
CP 10h             ; 내부 비교 결과는 40h-10h = 30h

30h = 0011 0000b   ; subtraction 결과의 bit 5 = 1
10h = 0001 0000b   ; 비교 operand의 bit 5 = 0

실제 Z80의 undocumented 동작에서는 이 CP의 F5/F3가 버려진 subtraction 결과가 아니라 비교 operand의 bit 5/3에서 옵니다. 따라서 위 예의 F5는 0입니다. 이 차이 때문에 “항상 결과 bit 복사”라고 가르치면 실제 CPU와 달라집니다.

BIT (IX+d)/(IY+d)에는 또 다른 규칙이 있다

IX = AB00h
d  = +05h

BIT 0,(IX+05h)     ; effective address = AB05h

이 indexed BIT 계열의 undocumented F5/F3는 테스트한 memory byte의 bit 5/3이 아니라 effective address의 상위 byte에서 옵니다. 이 예에서는 상위 byte가 ABh입니다. 즉 F5/F3의 출처 자체가 다른 instruction과 다릅니다.

F5/F3를 해석하는 원칙: debugger에서 F register를 직접 보면 bit 5와 3도 0/1로 나타날 수 있습니다. 두 bit는 공식 조건 flag가 아니지만 실제 Z80에서는 instruction에 따라 값이 변합니다. 또한 그 값의 출처가 instruction마다 같지 않으므로, 특정 코드가 F5/F3에 의존한다면 해당 instruction의 실제 F5/F3 동작 규칙을 따로 확인해야 합니다.

5-3. signed와 unsigned — byte에는 ‘255’나 ‘-1’이라는 꼬리표가 없다

같은 8bit pattern도 프로그램이 어떤 의미로 해석하느냐에 따라 숫자의 의미가 달라집니다.

1111 1111b = FFh

unsigned 8bit로 해석 → 255
signed 8bit로 해석   → -1

RAM이나 register에는 결국 11111111이라는 bit pattern이 저장될 뿐입니다. 그 값을 255로 볼지 -1로 볼지는 instruction과 프로그램 문맥이 결정합니다.

unsigned

0~255 같은 범위로 해석합니다. CP 뒤 C flag는 unsigned borrow 관계를 판단하는 데 직접 사용할 수 있습니다.

signed

-128~+127 같은 2의 보수 값으로 해석합니다. signed 대소 비교는 C 하나로 판단할 수 없으며 S와 P/V의 overflow 관계까지 고려해야 합니다.

주의: JP M은 “A가 signed로 더 작으면 jump”라는 명령이 아닙니다. M 조건은 S=1을 검사할 뿐입니다. signed 비교에서는 overflow 때문에 S만으로 대소 관계를 항상 판단할 수 없습니다.

5-4. CP는 A를 바꾸지 않고 ‘빼 본 결과’를 공식 flag에 남긴다

LD A,05h           ; A = 05h
CP 05h             ; A-05h를 한 것처럼 flags를 갱신
                    ; A 자체는 여전히 05h
CPU는 비교를 위해 A-operand 형태의 subtraction 결과를 만든 것처럼 flag를 계산합니다.
그 subtraction 결과를 A에 저장하지 않습니다. A는 원래 값을 유지합니다.
Z/C/S/H/P/V/N 같은 공식 flag는 CP 규칙에 따라 갱신됩니다. N은 1이 됩니다.
실제 F5/F3도 변하지만 공식 flag가 아니며, CP에서는 operand 쪽 bit 5/3을 따르는 undocumented 규칙이 있습니다.

5-5. CP와 flag를 직접 확인해 보자

A=05h, CP 05h → 내부 결과 00h 공식 flags: Z=1, C=0, S=0, H=0, P/V=0, N=1 undocumented: F5/F3는 CP operand 05h의 bit 5/3에서 옴 A 값은 05h 그대로 유지됩니다.

이 체험에서 공식 flag와 실제 undocumented F5/F3를 일부러 분리해 표시합니다. 둘을 같은 지위의 조건 flag처럼 생각하지 않기 위해서입니다.

5-6. CP 뒤의 Z와 C를 실제 숫자로 읽는다

같은 경우

LD A,05h           ; A=05h
CP 05h             ; 05h-05h = 00h
JR Z,EQUAL         ; Z=1이므로 분기

결과가 0이므로 Z=1입니다.

unsigned로 작은 경우

LD A,03h           ; A=03h
CP 05h             ; 03h-05h에서 borrow 발생
JR C,LOWER         ; C=1이므로 분기

unsigned 관점에서는 A가 05h보다 작습니다.

반대로 A=06h, CP 05h라면 subtraction 결과는 01h이므로 Z=0입니다. 이때 JR Z는 분기를 타지 않고 다음 instruction으로 진행합니다.

5-7. 조건 분기는 그 flag를 ‘마지막으로 바꾼 instruction’을 찾아야 한다

CP 05h             ; Z flag를 비교 결과에 맞게 변경
LD HL,9000h        ; Z flag를 변경하지 않음
JR Z,SAME          ; 따라서 이 Z는 여전히 CP 결과

JR Z가 바로 위의 LD HL,9000h를 검사하는 것이 아닙니다. LD HL,nn이 Z를 변경하지 않기 때문에 CPU에 남아 있는 Z는 앞의 CP가 만든 값입니다.

실전 추적 방법: 조건 jump를 만나면 “바로 위 instruction이 무엇인가?”가 아니라 “이 조건이 보는 flag를 마지막으로 변경한 instruction이 무엇인가?”를 찾습니다.

5-8. JP와 JR — 둘 다 실행 위치를 바꾸지만 방식이 다르다

JP

JP 9000h           ; PC를 9000h로 바꿈

16bit 목적지 주소를 instruction이 직접 사용합니다.

JR

JR LOOP            ; 현재 위치 근처의 label로 상대 이동

machine code에서는 JR 다음 PC를 기준으로 signed 8bit displacement를 사용합니다.

5-9. Zilog의 e와 실제 JR displacement를 다시 숫자로 확인한다

1장에서 본 것처럼 Zilog notation의 e와 machine code의 displacement byte를 구별해야 합니다.

5-12. DJNZ는 B를 직접 감소시키고 검사하는 반복 instruction이다

LD B,10h           ; B = 16, 최대 16회 반복

LOOP:
    INC HL         ; 다음 주소로 이동
    DJNZ LOOP      ; B=B-1, B≠0이면 LOOP로 상대 분기
10h → 0Fh → 0Eh → ... → 02h → 01h → 00h에서 종료
고급 참고 — B=00h에서 DJNZ를 시작하면?

DJNZ는 먼저 B를 1 감소시킨 뒤 0인지 검사합니다. 따라서 B=00h에서 실행하면 B는 FFh가 되고 분기합니다. 이런 경우 반복 경로에서는 B가 다시 00h가 될 때까지 총 256회 계열의 DJNZ 실행이 이어질 수 있으므로, 00h를 단순히 “0회 반복”이라고 읽으면 안 됩니다.

DJNZ의 중요한 점은 Z flag를 검사하는 instruction이 아니라는 것입니다. B를 감소시키고 그 B가 0인지 자체적으로 판단해 상대 분기합니다. 따라서 앞에서 Z가 어떤 값이었는지를 DJNZ loop 조건으로 읽으면 안 됩니다.

직접 실행: DJNZ가 B를 줄이며 반복하는 과정

초기 B를 정한 뒤 한 번씩 실행해 보세요. 매번 B가 먼저 1 감소하고, 그 결과가 0이 아니면 LOOP로 돌아갑니다. DJNZ는 Z flag를 검사하지 않습니다.

B=03h 아직 DJNZ를 실행하지 않았습니다.

6. CALL·RET·stack·index register

6-1. JP와 CALL은 무엇이 다른가

JP 9000h

PC를 9000h로 바꿉니다. 자동으로 돌아올 주소를 저장하지 않습니다.

현재 code ─────→ 9000h
VS

CALL 9000h

다음 instruction 주소를 stack에 저장한 뒤 PC를 9000h로 바꿉니다.

현재 code → stack에 복귀주소
          └────→ 9000h

6-2. CALL은 CPU 수준에서 무엇을 하는가

8000h : CD 00 90    CALL 9000h     ; 다음 instruction 주소 8003h를 보관
8003h : 3E 05       LD A,05h       ; RET 후 여기에서 계속
...
9000h : ...                         ; subroutine code
9005h : C9          RET             ; stack의 복귀 주소로 돌아감
CALL instruction의 다음 주소를 계산합니다. 위 예에서는 8003h입니다.
8003h를 stack에 저장합니다. SP가 2 감소하며 RAM에 16bit 값이 기록됩니다.
PC를 9000h로 바꿉니다. 이제 9000h부터 code를 실행합니다.
RET가 실행되면 stack에서 16bit 주소를 꺼내 PC에 넣습니다. 따라서 8003h로 돌아옵니다.
함수라는 표현: CALL/RET 조합이 일반적으로 subroutine, 즉 함수처럼 사용되기 때문에 “함수 호출”이라고 설명할 수 있습니다. 하지만 CPU 수준에서 CALL은 복귀 주소를 stack에 저장하고 PC를 바꾸는 instruction이고, RET는 stack top의 주소를 PC로 가져오는 instruction입니다.

직접 실행: CALL로 갔다가 RET로 돌아오기

예제는 PC=8000h, SP=F000h에서 시작합니다. CALL 9000h의 길이는 3byte이므로 복귀 주소는 8003h입니다.

8000h: CALL 9000h     ; 복귀 주소 8003h를 stack에 저장
8003h: LD A,05h       ; RET 뒤에 여기서 계속
9000h: RET            ; stack의 복귀 주소를 PC로 가져옴
PC=8000h SP=F000h stack은 비어 있습니다.

6-3. PUSH와 POP를 실제 RAM으로 본다

예를 들어 HL=1234h, SP=F000h라고 합시다.

PUSH HL            ; HL을 stack에 저장, SP는 최종적으로 2 감소
F000h
--
PUSH 전 SP가 가리키던 위치
EFFFh
12h

Z80 PUSH는 SP를 낮은 주소 방향으로 움직이며 16bit 값을 저장합니다. 최종적으로 SP=EFFEh가 됩니다. 메모리에서 낮은 주소 EFFEh에 low byte 34h, 그 다음 EFFFh에 high byte 12h가 있으므로 16bit 값을 little-endian으로 읽으면 1234h입니다.

POP DE             ; stack top의 16bit 값을 DE로 읽고 SP를 2 증가
DE = 1234h, SP = F000h

직접 실행: PUSH HL → POP DE

HL=1234h, DE=0000h, SP=F000h에서 시작합니다. PUSH를 누르면 stack RAM에 1234h가 저장되고 SP가 내려갑니다. 그 다음 POP DE를 누르면 같은 16bit 값이 DE로 들어가고 SP가 원래 위치로 돌아옵니다.

HL=1234h DE=0000h SP=F000h RAM[EFFEh]=-- RAM[EFFFh]=--

6-4. PUSH/POP은 왜 쓰는가

PUSH HL            ; 호출한 쪽의 HL 값을 잠시 보관
LD HL,9000h        ; 이 routine 안에서 HL을 작업용으로 사용
...
POP HL             ; 원래 HL 값을 복원
RET                ; 호출한 곳으로 복귀

routine 안에서 register를 자유롭게 쓰고 싶지만 호출한 쪽의 값을 망가뜨리고 싶지 않을 때 이런 형태가 자주 보입니다. 역분석할 때 PUSH와 POP 사이에서 register 역할이 바뀔 수 있다는 점도 기억해야 합니다.

6-5. EX와 EXX — 값을 계산하지 않고 register를 교환한다

EX DE,HL           ; DE와 HL의 16bit 내용을 서로 교환
EX AF,AF'          ; AF와 보조 AF'를 교환
EXX                ; BC/DE/HL과 보조 BC'/DE'/HL'를 한꺼번에 교환

debugger에서 HL 값이 갑자기 전혀 다른 값으로 바뀌었을 때 반드시 새 값을 계산했다고 생각할 필요는 없습니다. EX 또는 EXX로 이미 보관돼 있던 다른 register set과 교환했을 수도 있습니다.

6-6. IX와 IY — 기준 주소 + 작은 이동값

LD IX,9000h        ; IX를 기준 주소로 설정
LD A,(IX+05h)      ; 9000h + 5 = RAM[9005h]를 A로 읽음
LD B,(IX-02h)      ; 9000h - 2 = RAM[8FFEh]를 B로 읽음
effective address = IX 또는 IY + signed 8bit displacement

여기서 displacement는 JR에서 배운 것과 마찬가지로 signed 8bit이므로 -128~+127 범위를 가집니다. IX/IY는 table entry나 여러 field가 일정한 offset으로 배치된 데이터를 다룰 때 편리합니다.

고정 역할이 아님: “IX는 구조체 register”라고 외우는 것이 아니라, Z80 instruction 자체가 (IX+d), (IY+d) 접근을 지원하기 때문에 그런 데이터 구조에 사용하기 편한 것입니다.

직접 계산: IX+d가 가리키는 실제 주소

IX 기준 주소와 signed displacement를 바꾸어 effective address를 계산해 보세요. d는 -128~+127 범위입니다.

IX=9000h, d=+5 → effective address=9005h

7-2. LDIR은 그 LDI 계열 동작을 BC=0까지 반복한다

LD HL,8000h        ; source = 8000h
LD DE,9000h        ; destination = 9000h
LD BC,0100h        ; 256 bytes
LDIR               ; BC가 0이 될 때까지 순방향 block transfer
8000h~80FFh → 9000h~90FFh, 256 bytes

LDIR을 보면 먼저 HL=source, DE=destination, BC=count라는 역할을 확인할 수 있습니다. 이 역할은 LDIR instruction의 동작 자체가 정합니다. 다만 LDIR이 끝난 뒤에는 HL과 DE가 복사 끝 다음 주소로 이동하고 BC는 0000h가 됩니다.

고급 참고 — LDIR/CPIR에서 BC=0000h

반복형 block instruction은 내부 동작에서 counter를 감소시키며 반복 여부를 판단합니다. 따라서 시작 시 BC=0000h를 단순히 “처리할 byte가 0개”라고 해석하면 실제 CPU 동작과 어긋날 수 있습니다. 예를 들어 LDIR은 첫 전송 뒤 BC가 FFFFh가 되어 반복을 계속할 수 있습니다. 역분석에서는 counter의 시작값과 instruction 자체의 반복 조건을 함께 확인합니다.

7-3. LDI와 LDIR을 직접 실행해 보자

source에 41h, 52h, 63h 세 byte가 있다고 가정합니다. LDI 1회 버튼은 한 byte만 옮기고, LDIR은 남은 byte를 끝까지 옮깁니다.

Source 8000h: [41 52 63] Dest 9000h: [00 00 00] HL=8000h DE=9000h BC=0003h

7-4. LDD / LDDR은 주소가 감소하는 방향으로 움직인다

LDD                ; (HL)→(DE), HL--, DE--, BC--
LDDR               ; 같은 방향의 동작을 BC=0까지 반복

앞에서부터 뒤로 복사하는 LDI/LDIR과 달리 LDD/LDDR은 높은 주소에서 낮은 주소 방향으로 이동합니다. 겹치는 메모리 영역을 옮기거나 역방향 처리가 필요한 code에서 볼 수 있습니다.

7-5. CPI / CPIR — 메모리를 순서대로 검색한다

LD A,00h           ; 찾을 값
LD HL,9000h        ; 검색 시작 주소
LD BC,0100h        ; 최대 256byte
CPIR               ; A와 (HL)을 비교하며 앞으로 진행

CPI 계열은 A와 (HL)을 비교한 뒤 HL을 증가시키고 BC를 감소시킵니다. CPIR은 같은 값을 찾았거나 BC가 0이 될 때까지 이 동작을 반복합니다. A 자체는 비교값으로 유지됩니다.

역분석에서의 단서: 종료 byte 00h를 찾거나 특정 marker를 검색하는 code에서 CPIR 같은 instruction이 보이면 “연속 메모리 검색” 가능성을 생각할 수 있습니다.

SLA r왼쪽으로 shift, bit 7은 Carry로 나감, bit 0에는 0

8. I/O·interrupt·prefix opcode

8-1. memory access와 I/O access는 서로 다른 공간이다

Memory

LD A,(005Ch)       ; memory address 005Ch에서 읽음
LD (005Ch),A       ; memory address 005Ch에 씀

I/O

IN A,(5Ch)         ; I/O port의 값을 A로 입력
OUT (5Ch),A        ; A를 I/O port로 출력

둘 다 숫자 5Ch가 보이지만 같은 좌표가 아닙니다. Z80에는 memory access cycle과 I/O access cycle이 따로 있으며 PC-88의 hardware는 I/O port를 통해 GVRAM 선택, sound, disk subsystem interface 같은 기능을 제어합니다.

대표적인 착각: OUT (5Ch),A를 “RAM 005Ch에 A를 쓴다”고 읽으면 안 됩니다. 이것은 I/O write입니다.

8-2. IN A,(n) / OUT (n),A를 읽는 법

IN A,(5Ch)         ; 즉시 port 번호를 사용한 입력
OUT (5Ch),A        ; A의 값을 즉시 port 번호 쪽으로 출력

일반적인 PC-88 code를 읽을 때는 먼저 “memory가 아니라 I/O 접근”이라는 점과 낮은 8bit port 번호를 확인하면 됩니다. Z80 bus 수준에서는 이 즉시 I/O 형식에서 A의 값도 상위 address line 쪽에 나타나지만, 실제 기기가 어느 address line까지 decode하는지는 hardware 설계에 따라 달라집니다.

PC-88에서의 사고 순서: OUT (5Ch),A를 보면 먼저 “I/O port 5Ch 접근”이라고 판정하고, 그 다음 1부에서 배운 PC-88 I/O map을 대조해 이 port가 어떤 hardware 기능을 선택하는가를 확인합니다.

직접 비교: 같은 5Ch라도 Memory와 I/O는 다른 공간

각 버튼은 같은 초기 상태 A=AAh, Memory[005Ch]=11h, I/O port 5Ch=22h에서 해당 instruction 하나만 실행합니다. 어느 공간이 바뀌는지 서로 독립적으로 비교하세요.

Memory space[005Ch] = 11h
I/O spaceport 5Ch = 22h
A=AAh Memory와 I/O는 서로 독립된 공간입니다.

8-3. IN r,(C) / OUT (C),r는 BC가 I/O address 형성에 참여한다

LD BC,12F0h        ; B=12h, C=F0h
IN A,(C)           ; BC가 I/O address bus에 사용되는 형식
OUT (C),A          ; A를 같은 방식의 I/O address로 출력

초보 단계에서 C만 “port 번호 register”라고 외우면 정확하지 않습니다. 이 형식은 Z80의 I/O cycle에서 BC 전체가 address bus에 나타납니다. 다만 실제 PC-88 장치가 상위 address bit까지 모두 decode하는지는 장치별 hardware 설계를 봐야 합니다.

8-4. INI를 먼저 해부하면 INIR도 어렵지 않다

INI                ; I/O에서 1byte 입력 → (HL), HL++, B--

INI 계열은 I/O에서 들어온 byte를 메모리로 연속 전송할 때 유용합니다. 기본적으로 C를 포함한 BC가 I/O address를 형성하고, 읽은 byte를 HL이 가리키는 메모리에 저장한 뒤 HL을 증가시키고 B를 감소시킵니다.

INIR               ; INI 계열 동작을 B가 0이 될 때까지 반복
OUTI               ; (HL)의 byte를 I/O로 출력, HL++, B--
OTIR               ; OUTI 계열 동작을 B가 0이 될 때까지 반복
왜 PC-88 분석에서 중요하나: disk subsystem과의 byte transfer 같은 low-level code에서 block I/O instruction이 보일 수 있습니다. 이때 단순히 “특수한 IN”이라고 넘기지 않고 I/O → memory, pointer 이동, counter 감소라는 세 가지 상태 변화를 같이 봐야 합니다.

8-5. DI / EI / HALT와 interrupt는 입문 수준에서 이렇게 읽는다

DI                 ; maskable interrupt를 받지 않도록 설정
...                ; timing이나 상태 변경이 민감한 구간
EI                 ; maskable interrupt 허용 상태로 복원

HALT               ; 정상 instruction 진행을 멈추고 interrupt 등을 기다림

DI와 EI는 interrupt 허용 상태를 제어합니다. EI의 경우 maskable interrupt가 즉시 그 instruction 중간에 들어오는 것이 아니라, 다음 instruction을 실행한 뒤부터 받아들일 수 있도록 설계되어 있습니다. HALT는 정상 code 진행을 멈추고 interrupt가 발생하는 등의 조건을 기다리는 데 사용됩니다.

IM 0, IM 1, IM 2는 Z80의 interrupt mode를 선택합니다. 2부에서는 존재와 기본 목적까지만 알고, interrupt routine 전체 구조는 실제로 필요할 때 더 깊게 분석하면 됩니다.

8-6. RST는 짧은 CALL처럼 생각하면 입문하기 쉽다

RST 08h            ; 복귀 주소를 stack에 저장하고 0008h로 이동
RST 38h            ; 복귀 주소를 stack에 저장하고 0038h로 이동

RST는 정해진 낮은 주소 00h, 08h, 10h ... 38h 중 하나로 이동합니다. CALL과 마찬가지로 복귀 주소를 stack에 저장하므로 작은 ROM routine 호출이나 interrupt 관련 code에서 볼 수 있습니다.

8-7. CB / ED / DD / FD는 ‘앞에 붙는 확장 opcode’일 수 있다

Z80 instruction set은 1byte opcode만으로 끝나지 않습니다. 다음과 같은 prefix byte 뒤에 추가 opcode와 operand가 붙는 instruction이 있습니다.

prefix주로 연결되는 계열예
CBBIT, SET, RES, rotate/shift 계열CB 7F
EDblock transfer/I/O, interrupt 관련 등 확장 명령ED B0 = LDIR
DDIX 관련 instructionDD 7E 05
FDIY 관련 instructionFD 7E 05
DD7E05→LD A,(IX+05h)

이 예는 세 byte가 하나의 instruction입니다. 따라서 hex dump에서 DD를 하나의 독립 instruction, 7E를 다음 instruction으로 끊어 읽으면 완전히 잘못된 disassembly가 됩니다.

9-2. disassembler가 보여줬다고 반드시 code는 아니다

메모리에는 결국 byte만 있습니다. 데이터 영역을 강제로 disassemble해도 byte pattern이 우연히 Z80 opcode 조합으로 해석되기 때문에 그럴듯한 instruction 목록이 나옵니다.

실제로 code라면

PC가 그 위치를 instruction으로 fetch하고, CALL/JP 같은 실행 흐름이 들어오며, 주변 code와 의미 있는 제어 흐름이 만들어집니다.

실제로 data라면

프로그램이 LD나 table lookup 등으로 읽을 뿐, PC가 그 byte를 instruction으로 실행하지 않을 수 있습니다.

따라서: “disassembler 창에 assembly가 보인다 = 그 영역은 code다”라고 확정하지 마십시오. 실행 흐름과 memory access를 함께 확인해야 합니다.

9-3. PC-88에서는 CPU address만 알아도 실제 메모리를 확정할 수 없는 경우가 있다

LD A,(2000h)       ; Z80 수준에서 확정: CPU address 2000h를 읽는다

하지만 1부에서 배웠듯 PC-88은 memory mapping과 bank switching을 사용합니다. 따라서 이 한 줄만 보고 “물리 Main RAM 2000h를 읽었다”고 확정하면 안 됩니다. 당시 mapping 상태에 따라 같은 CPU address 뒤에 ROM이나 다른 RAM bank가 보일 수 있습니다.

코드에서 확정 가능CPU가 2000h라는 논리 주소를 읽는다.
추가 확인 필요당시 어떤 ROM/RAM mapping이 선택돼 있었는가.
역분석 기록주소뿐 아니라 bank/mapping 상태도 함께 기록.

9-4. register의 역할은 한 줄만 보고 정하지 않는다

LD HL,9000h        ; 여기까지만 보면 HL의 역할은 아직 모름
LD A,(HL)          ; HL을 memory address로 사용
INC HL             ; 다음 주소로 이동
LD B,(HL)          ; 다음 byte도 읽음

이제야 “이 코드 블록에서 HL은 순차 데이터 pointer 역할을 하는 것으로 보인다”고 해석할 근거가 생깁니다.

역분석에서 세 층을 구분:
사실 — HL에 9000h가 들어갔다. (HL)을 읽었다. HL이 증가했다.
해석 — 이 블록에서 HL은 데이터 pointer 역할을 한다.
추정 — 이 데이터는 문자열일 가능성이 있다. 실제 화면/호출 관계를 더 확인해야 한다.

9-5. 한 줄 → 작은 블록 → 루틴으로 추상화한다

한 줄

INC HL             ; HL을 1 증가

여기서는 “HL이 1 증가한다”가 전부입니다.

작은 블록

LD A,(HL)          ; 현재 byte 읽기
INC HL             ; 다음 byte 주소로 이동
CP 00h             ; 읽은 byte가 00h인지 검사

세 줄을 묶으면 “byte 하나를 읽고 pointer를 진행한 뒤 00h인지 검사한다”고 요약할 수 있습니다.

루틴

LOOP:
    LD A,(HL)      ; 현재 byte 읽기
    INC HL         ; 다음 byte 주소로 이동
    CP 00h         ; 종료값인지 검사
    JR NZ,LOOP     ; 00h가 아니면 계속 읽기

이제 “00h가 나올 때까지 byte stream을 순차적으로 읽는 loop”라고 한 단계 높은 수준으로 설명할 수 있습니다.

역분석의 목표: 최종적으로는 LD, CP, JR을 한글 단어로 번역하는 것이 아니라 그 조합이 어떤 데이터 구조와 실행 규칙을 구현하는지 알아내는 것입니다.

10. 보조 주석을 줄여 가며 실제 코드 읽기

마지막에는 같은 code를 여러 번 보면서 주석이라는 보조바퀴를 단계적으로 제거합니다.

10-1. 1단계 — 모든 줄에 자세한 주석

LD E,(HL)          ; HL이 가리키는 현재 byte를 E로 읽음
INC HL             ; HL을 1 증가시켜 다음 byte를 가리킴
LD A,E             ; E의 값을 A로 복사
LD (0C84h),A       ; 원래 byte 값을 memory 0C84h에 보관
AND 0Fh            ; A의 상위 4bit를 버리고 하위 4bit만 남김
CP 01h             ; A가 01h인지 비교하고 flags를 갱신
JP Z,0452h         ; Z=1, 즉 같으면 0452h로 이동

10-2. 2단계 — 최소한의 주석만 남긴다

LD E,(HL)          ; byte 읽기
INC HL             ; pointer++
LD A,E
LD (0C84h),A
AND 0Fh
CP 01h
JP Z,0452h

LD E,(HL)
INC HL
LD A,E

10-5. 이 블록에서 확정할 수 있는 사실

HL이 가리키는 1byte를 E로 읽습니다. 따라서 실행 직전 HL은 어떤 data 위치를 가리키고 있습니다.
HL을 1 증가시킵니다. 읽은 뒤 다음 byte 쪽으로 pointer를 진행합니다.
읽은 원본 값을 A와 0C84h에 전달합니다. 0C84h에는 mask 전의 원본 byte가 저장됩니다.
A에는 AND 0Fh가 적용됩니다. 이후 비교에 사용하는 것은 원본의 하위 4bit입니다.
하위 4bit가 01h이면 0452h로 이동합니다. 이것은 JP Z의 조건으로 확정할 수 있습니다.

10-6. 여기서부터는 해석 또는 추정이다

여러 값과 비교해 서로 다른 주소로 분배하는 code가 뒤에 이어진다면 이 블록을 dispatcher나 command decoder처럼 해석할 수 있습니다. 하지만 위 7줄만으로 “반드시 문자 command dispatcher다”라고 확정할 수는 없습니다. 호출 관계, 0452h의 code, HL이 가리키는 data 내용 등을 더 확인해야 합니다.

좋은 역분석 문장: “HL stream에서 1byte를 읽고 하위 4bit를 기준으로 01h 여부를 검사해 0452h로 분기한다.”

성급한 문장: “이건 무조건 대사 출력 명령 1번이다.” — 그런 역할을 확정하려면 추가 증거가 필요합니다.

확인

확인 문제

Q1. LD A,B에서 값은 어느 방향으로 이동하는가?
B → A입니다. B의 값이 A로 복사되고 B 자체는 바뀌지 않습니다.
Q2. HL과 (HL)은 무엇이 다른가?
HL은 register 안의 16bit 값 자체이고, (HL)은 그 값이 가리키는 memory address의 내용입니다.
Q3. RAM[9000h]=34h, RAM[9001h]=12h일 때 LD HL,(9000h)의 결과는?
HL=1234h입니다. Z80의 little-endian 배치 때문에 낮은 주소 9000h의 34h가 low byte가 됩니다.
Q4. INC HL은 RAM[HL]의 byte를 증가시키는가?
아닙니다. HL register의 16bit 값을 1 증가시킵니다. 메모리 byte를 증가시키려면 INC (HL) 형태를 사용합니다.
Q5. LD HL,FFFFh 다음에 INC HL을 실행하면?
HL=0000h가 됩니다. 16bit 범위를 넘어가 wrap-around가 발생합니다.
Q6. XOR A가 A를 0으로 만드는 이유는?
어떤 bit도 자기 자신과 XOR하면 0이므로 A XOR A의 결과는 항상 00h입니다.
Q7. CP 05h는 A 값을 05h만큼 감소시키는가?
아닙니다. A-05h를 한 것처럼 flags를 갱신하지만 A 자체는 바꾸지 않습니다.
Q8. CP 다음에 LD HL,9000h가 있고 그 다음 JR Z가 있다면 JR Z는 반드시 LD의 결과를 보는가?
아닙니다. 일반적인 LD HL,nn은 Z flag를 바꾸지 않으므로 JR Z는 그 전에 Z를 마지막으로 변경한 CP 결과를 그대로 사용할 수 있습니다.
Q9. 8000h에 2byte JR instruction이 있고 displacement가 -2라면 목적지 계산 기준은 어디인가?
JR instruction을 모두 읽은 뒤의 PC인 8002h가 기준입니다. 8002h + (-2) = 8000h입니다.
Q10. 조건 JR이 성립하지 않으면 CPU는 어디로 가는가?
그 JR instruction 다음 instruction으로 계속 진행합니다. 이것이 fall-through path입니다.
Q11. DJNZ는 어떤 register를 감소시키는가?
B register를 1 감소시킨 뒤 B가 0이 아니면 상대 분기합니다.
Q12. JP와 CALL의 가장 중요한 차이는?
CALL은 다음 instruction의 주소를 stack에 복귀 주소로 저장한 뒤 이동합니다. JP는 자동으로 복귀 주소를 저장하지 않습니다.
Q13. HL=1234h, SP=F000h에서 PUSH HL 후 최종 SP는?
EFFEh입니다. 16bit 값을 stack에 넣으면서 SP가 총 2 감소합니다.
Q14. LDI 한 번을 실행하면 HL, DE, BC는 어떻게 변하는가?
(HL)의 1byte가 (DE)로 복사되고 HL은 +1, DE는 +1, BC는 -1 됩니다.
Q15. LDIR은 LDI와 무엇이 다른가?
LDIR은 LDI 계열의 순방향 block transfer 동작을 BC가 0이 될 때까지 반복합니다.
Q16. CPIR은 무엇을 반복하는가?
A와 (HL)을 비교하고 HL을 증가, BC를 감소하는 검색 동작을 일치하거나 BC=0이 될 때까지 반복합니다.
Q17. OUT (5Ch),A는 RAM 005Ch에 A를 쓰는가?
아닙니다. I/O write instruction입니다. PC-88에서는 해당 I/O port가 어떤 hardware 기능인지 별도의 I/O map으로 확인해야 합니다.
Q18. DD 7E 05를 세 개의 독립 instruction으로 읽어도 되는가?
안 됩니다. 이 경우 DD prefix, 7E opcode, 05 displacement가 합쳐져 LD A,(IX+05h)라는 하나의 instruction을 구성합니다.
Q19. disassembler가 assembly를 보여주면 그 영역은 반드시 code인가?
아닙니다. data byte도 강제로 disassemble하면 opcode처럼 해석될 수 있습니다. 실제 실행 흐름이 그 위치를 instruction으로 fetch하는지 확인해야 합니다.
Q20. LD HL,9000h 한 줄만 보고 “HL은 문자열 pointer다”라고 확정해도 되는가?
안 됩니다. (HL)을 읽고 HL을 증가하는 등의 주변 동작을 더 확인한 뒤 “이 루틴에서 순차 데이터 pointer 역할을 한다”처럼 근거에 맞게 해석해야 합니다.
Q21. Zilog 표기의 e와 JR 기계어의 displacement byte는 같은 값인가?
항상 같지 않습니다. Zilog notation의 e는 현재 JR instruction 시작 위치 기준 offset이고, 실제 기계어 displacement는 2byte JR을 읽고 난 뒤의 PC 기준입니다. 예를 들어 8000h→8008h라면 e=+8, machine displacement=+6입니다.
Q22. PUSH qq에서 qq는 “아무 16bit register”라는 뜻인가?
아닙니다. qq는 BC, DE, HL, AF의 집합입니다. SP는 포함되지 않습니다. ss, pp, rr 같은 다른 기호는 서로 다른 허용 register-pair 집합을 뜻합니다.
Q23. F register의 bit 5와 bit 3은 항상 0인가?
아닙니다. Zilog 공식 문서에서는 Not Used로 취급하지만 실제 Z80에서는 여러 instruction에 의해 값이 변하는 undocumented F5/F3 동작이 있습니다.
Q24. F5/F3는 항상 연산 결과의 bit 5/3을 복사하는가?
아닙니다. 그런 계열이 많지만 만능 규칙은 아닙니다. 예를 들어 CP에서는 비교 operand의 bit 5/3에서 오고, indexed BIT 계열에서는 effective address의 상위 byte에서 오는 특수 동작이 알려져 있습니다.
Q25. FFh는 255인가, -1인가?
저장된 bit pattern 자체는 FFh입니다. unsigned 8bit로 해석하면 255, signed 8bit 2의 보수로 해석하면 -1입니다. 문맥과 instruction이 해석을 결정합니다.
