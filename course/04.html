실행 중인 게임에서 원인을 찾는 과정

0~3부에서 PC-88의 구조, Z80 code, 플로피와 D88, MAIN/SUB CPU를 배웠습니다. 이제 그 지식을 실제 실행 중인 게임에 대입합니다.

현상 발견→정지→PC / Register→Code / Memory→한 단계 실행→원인 좁히기
4부의 범위: 특정 게임의 데이터를 끝까지 역추적하는 단계가 아니라, 먼저 debugger라는 관찰 도구를 제대로 사용하는 법에 집중합니다.

4. 왜 실제 PC-88 대신 Emulator Debugger를 사용하는가

실제 PC-88에도 machine-language monitor 같은 조사 수단이 있었습니다. 하지만 breakpoint, memory access 감시, register 관찰, single-step 등을 같은 상태에서 반복하려면 emulator debugger가 훨씬 편리합니다.

분석 대상
PC-88 프로그램→Emulator로 동작 재현→Debugger로 상태 관찰
Emulator를 쓰는 이유는 다른 기계를 분석하기 위해서가 아니라 PC-88의 동작을 사람이 관찰하기 쉽게 만들기 위해서입니다.

19. CALL과 RET를 따라가면 PC 이동과 복귀를 실제 상태로 볼 수 있다

C13D CD32C2  CALL C232H
              ↓ step
C256 C9      RET
------> C140 0B  DEC BC
이 예에서 Step Over의 핵심은 “CALL 대상의 모든 instruction을 화면에 하나씩 보여 주지 않고, routine이 끝난 뒤 호출 다음 주소에서 다시 관찰한다”는 것입니다.
실제 선택된 경로

20. 조건분기와 Loop는 가능한 경로보다 이번 실행에서 실제 선택된 경로를 본다

스크린샷 13에서 현재 instruction은 C143 JR NZ,C13D였습니다. 당시 Z flag가 0이므로 NZ 조건이 참이 되어 실제 PC가 C13Dh로 이동했습니다.

C143 JR NZ,C13D
Z = 0
    ↓ step
PC = C13D
Disassembly만 보면 두 경로가 모두 보입니다. Debugger는 이번 실행에서 어느 경로가 실제 선택됐는지 보여 줍니다.
Memory 밖의 사건

21. PC-88에서는 I/O Port 접근도 중요한 사건이 될 수 있다

Z80의 IN, OUT은 memory가 아니라 I/O port와 데이터를 주고받습니다. 키 입력, sound, disk subsystem 등 hardware와 연결된 처리를 조사할 때 I/O instruction이 단서가 됩니다.

처음부터 모든 I/O port를 추적할 필요는 없습니다. memory와 code 흐름을 먼저 잡고, hardware 접근이 원인으로 의심될 때 I/O까지 확장하는 것이 좋습니다.
PC-88의 두 CPU 환경

22. 지금 보고 있는 Code가 MAIN CPU인지 SUB CPU인지 확인해야 할 때가 있다

PC-88의 대표적인 FDD 구성에서는 MAIN CPU와 disk 처리를 담당하는 SUB CPU가 따로 동작합니다. 따라서 PC가 같다는 이유만으로 같은 CPU의 address라고 생각하면 안 됩니다.

이 스크린샷의 목적은 특정 port를 분석하는 것이 아니라 현재 어느 CPU를 보고 있는지 구분하는 법을 확인하는 것입니다.
정지 후 고정 루틴

23. 처음 멈췄을 때는 매번 같은 순서로 보면 단서를 놓치기 어렵다

1. CPU와 PC를 본다. MAIN/SUB와 현재 실행 위치를 확인합니다.
2. 현재 instruction과 주변 disassembly를 본다. 지금 무엇을 하고 다음 어디로 갈 수 있는지 봅니다.
3. 주요 register를 code와 연결한다. 주소나 작업값으로 쓰이는 register를 찾습니다.
4. 필요한 memory를 본다. pointer가 가리키는 실제 byte를 확인합니다.
5. 조건분기라면 flag를 본다. 실제 선택될 경로를 판단합니다.
6. 필요한 경우 한 instruction 실행한다. 전후 상태를 비교합니다.
7. 질문에 맞게 breakpoint를 바꾼다. PC/READ/WRITE 중 다음 단서를 줄 수 있는 것을 선택합니다.
Debugger는 처음부터 끝까지 전부 step하는 도구가 아닙니다. 관심 없는 구간은 실행하고, 중요한 사건을 breakpoint로 잡은 뒤 필요한 몇 instruction만 자세히 봅니다.

확인 문제

4부 확인 문제

1. Debugger가 필요한 가장 기본적인 이유는?
실행 중인 프로그램을 원하는 순간에 멈추고 PC, register, memory, code 상태를 관찰해 실제 실행 과정을 확인하기 위해서입니다.
2. Disassembly와 동적 실행 추적의 차이는?
Disassembly는 존재하는 code와 가능한 흐름을 보여 주고, debugger는 실제 실행된 code와 실제 값을 확인하게 합니다.
3. QUASI88 전용 강좌인가?
아닙니다. 공통 debugger 개념을 배우며 QUASI88은 대표 실습 예시입니다.
4. Routine이 실제로 언제 실행되는지 알고 싶다면?
그 routine의 실행 주소에 PC/Execution breakpoint를 생각합니다.
5. 어떤 RAM data를 누가 읽는지 알고 싶다면?
READ breakpoint/watchpoint를 사용합니다.
6. 어떤 RAM 값이 왜 바뀌었는지 알고 싶다면?
WRITE breakpoint/watchpoint를 사용합니다.
7. Breakpoint에 걸린 직후 reg를 반드시 다시 입력해야 하나?
아닙니다. QUASI88 Monitor는 breakpoint hit 시 CPU/register 상태를 자동 표시합니다.
8. READ/WRITE breakpoint에서 화살표가 항상 접근 instruction을 가리키나?
아닙니다. 접근 instruction 실행 뒤 정지하여 PC가 다음 instruction을 가리킬 수 있으므로 바로 앞 instruction도 확인해야 합니다.
9. Step Into와 Step Over의 차이는?
Step Into는 CALL 내부로 들어가고, Step Over는 routine을 실행한 뒤 호출 다음 위치에서 다시 관찰합니다.
10. JR NZ 앞에서 Z=0이면?
NZ 조건이 성립하므로 분기합니다. 스크린샷 13에서는 C13Dh로 실제 이동했습니다.
11. PC address와 D88 file offset은 같은 좌표인가?
아닙니다. PC는 CPU address space, D88 offset은 disk image 파일의 byte 위치입니다.
12. MAIN CPU만 보면 항상 충분한가?
아닙니다. disk subsystem 같은 대상은 SUB CPU 확인이 필요할 수 있습니다.
