01 · CLASSIFY

문자처럼 보인다고 모두 같은 Font를 쓰는 것은 아니다

이번 장면은 이벤트 1의 첫 문장입니다. 정상 상태와 KANJI1.ROM을 제거한 뒤 재시작한 상태를 비교하고, 실제 일본어 문자가 나타나기 시작할 때 강제로 멈춥니다. ROM 제거 실험에서는 원본을 반드시 백업하고, 에뮬레이터의 대체 ROM 경로나 이미 로드된 캐시 가능성에 주의합니다.

세 PNG는 이번 실습에서 제공받았지만 아직 GitHub의 images/course06/에 등록하지 않았다. 실제 파일을 등록하면 이 자리의 캡처 박스를 <img>로 교체한다.

이번 화면에서 관찰

ROM을 제거한 비교 화면에서는 배경·인물은 보이지만 문자 영역이 정상 표시되지 않습니다.

다음에 확인할 것

이 차이는 Kanji ROM 의존성의 단서입니다. 실제로 어떤 I/O 명령이 실행되는지는 디버거에서 별도로 확인해야 합니다.

02 · BREAK AND OBSERVE

강제로 멈춘 PC를 문자 출력 코드라고 가정하지 않는다

03.PNG에서 「雨が」까지 화면에 보였을 때 강제로 Monitor에 진입했습니다. PC=04BD는 0292h를 읽어 D와 비교하는 대기 루프였습니다. 첫 문자를 막 그리기 시작하는 지점과 혼동하지 않습니다.

QUASI88> reg [MAIN] AF:0993[S..H..NC] BC:0000 DE:0AD0 HL:96A3 IX:0000 PC:04BD IY:E55C SP:00FA 04C1 38FA JR C,04BDH ------> 04BD 3A9202 LD A,(0292H) 04C0 BA CP D 04BD LD A,(0292H) 04C0 CP D 04C1 JR C,04BDH 04C3 XOR A 04C4 LD (0292H),A 04C7 POP DE 04C8 RET
현재 PC가 대기 처리 안이라면, 그 대기를 누가 호출했는지 어디서 확인할 수 있을까요?

5부에서 사용한 Stack 확인을 그대로 적용합니다. 지금 실행을 재개하지 않고 반환 주소 후보부터 조사합니다.

03 · FIND THE CALLER

Stack의 4F 04에서 반환 주소 044Fh를 찾는다

QUASI88> dump 0x00FA #16 00FA : D0 18 4F 04 CB 01 31 00 01 CD E4 01 3E 48 D3 32 QUASI88> disasm 0x0443 #32 0443 CD8F0B CALL 0B8FH 0446 3E08 LD A,08H 0448 D332 OUT (32H),A 044A 3E0A LD A,0AH 044C CDAE04 CALL 04AEH 044F C3E402 JP 02E4H

04AEh에서는 PUSH DE로 기존 DE를 보관한 상태이므로, SP가 가리키는 D0 18은 저장된 DE입니다. 바로 다음 4F 04를 little-endian으로 읽으면 반환 주소 044Fh가 됩니다.

실측 값SP=00FAh, 다음 반환 주소 044Fh호출 관계0443 CALL 0B8F → 044C CALL 04AE → 044F JP 02E4다음 질문02E4h로 돌아온 뒤, 다음 대사 Byte를 어디서 읽는가?

왜 저장된 DE가 18D0h인가?

뒤의 출력 루틴에서 행 하나를 읽을 때마다 INC DE가 실행되는 것을 확인합니다. 두 번째 문자 「が」의 시작값 18C0h에 16행을 더하면 18D0h입니다. 값의 차이를 Script 불일치로 단정하지 않습니다.

04 · SCRIPT READER

반환 경로에서 실제 Script consumer를 발견한다

QUASI88> disasm 0x02E4 #48 02E4 LD A,(02CCH) 02E7 BIT 7,A 02E9 RET Z 02EA XOR A 02EB OUT (35H),A 02ED LD E,(HL) 02EE INC HL 02EF LD A,E 02F0 LD (0C84H),A 02F3 AND 0FH 02F5 JP Z,03B8H ... 031B CP 08H 031D JP Z,03B8H QUASI88> dump 0x969F #16 969F : B8 62 C8 18 48 38 38 39 78 28 B8 38 60 12 60 12 QUASI88> dump 0x0C84 #1 0C84 : C8 18 03 02 00 D4 EB D0 EB 00 00 00 00 00 00 00

현재 HL=96A3h이고 0C84h=C8h입니다. 이번 장면에서 이미 처리한 두 Token의 시작 위치를 확인할 수 있습니다. 02EDh는 Script의 첫 바이트를 E로 읽고, 0C84h에 저장한 뒤 하위 4비트로 분기합니다.

주소실제 Byte장면의 문자다음 HL
969FhB8 62雨96A1h
96A1hC8 18が96A3h
96A3h48 38や — 다음 출력 대상96A5h

Token과 JIS를 같은 것으로 취급하지 않는다

B8 62는 이 게임에서 확인한 Script Byte입니다. 0B8Fh에 전달되는 Kanji 접근 주소는 별도 명령으로 구성됩니다. 또한 이번 분기가 모든 제어 Token의 길이·의미까지 설명하는 것은 아닙니다.

05 · TRACE TOKEN BRANCH

상위 비트와 두 번째 바이트에서 Glyph 주소를 구성한다

QUASI88> disasm 0x03B8 #80 03B8 LD A,E 03B9 AND F0H 03BB LD E,A 03BC LD D,(HL) 03BD INC HL 03BE LD A,(0C84H) 03C1 AND 08H 03C3 JP NZ,043FH ... 043F LD A,48H 0441 OUT (32H),A 0443 CALL 0B8FH 0446 LD A,08H 0448 OUT (32H),A 044A LD A,0AH 044C CALL 04AEH 044F JP 02E4H
입력 Token분기와 변환출력 시작 시 DE
B8 62 (雨)B8 & 0F = 08, E=B0, D=6262B0h
C8 18 (が)C8 & 0F = 08, E=C0, D=1818C0h
48 38 (や)48 & 0F = 08, E=40, D=383840h

03BE~03C3은 저장해 둔 Token 첫 바이트의 08h 비트를 다시 검사합니다. 이번 세 Token에서는 043Fh를 거쳐 같은 출력 루틴을 호출하지만, 다른 조건의 처리는 구분해 두어야 합니다.

이번 장면에서 실제로 연결한 경로

번호는 수강생에게 처음부터 주는 정답이 아니라, 각 관찰이 끝난 뒤 기록한 결과입니다.

flowchart TD
  A["화면에 雨が 표시 / 강제 Monitor"] --> B["04BD 대기 루프 / HL 96A3"]
  B --> C["stack 4F 04 → 반환 주소 044F"]
  C --> D["0443 CALL 0B8F / 044C CALL 04AE"]
  D --> E["044F JP 02E4 / Script consumer 02ED"]
  E --> F["하위 nibble 08 / 03B8 분기"]
  F --> G["043F → 0443 / 문자 출력 0B8F"]
  G --> H["0BE1 / OUT E8·E9 / IN E8·E9"]
  H --> I["BC Glyph → 0BFE·0C00 → 화면 접근 메모리"]
06 · KANJI ROM I/O

실제로 다음 글자 「や」를 읽기 직전의 레지스터를 잡는다

앞선 호출 관계에서 찾은 0B8Fh는 출력의 시작 주소를 준비하고 0BE1h를 16번 호출합니다. 이미 「雨が」가 출력된 현재 상태에서 다음 글자를 확인하기 위해 실측된 breakpoint를 사용합니다.

QUASI88> break 0x0BE1 #1 set break point MAIN - #1 [ PC : 0BE1H ] QUASI88> go *** Break at 0BE1H *** ( MAIN[#1] : PC ) [MAIN] AF:3800[........] BC:0000 DE:3840 HL:EBD4 PC:0BE1 SP:004E 0B9E CDE10B CALL 0BE1H ------> 0BE1 D3EB OUT (EBH),A QUASI88> disasm #24 0BE1 OUT (EBH),A 0BE3 LD A,E 0BE4 OUT (E8H),A 0BE6 LD A,D 0BE7 OUT (E9H),A 0BE9 OUT (EAH),A 0BEB NOP 0BEC NOP 0BED IN A,(E8H) 0BEF LD C,A 0BF0 IN A,(E9H) 0BF2 LD B,A 0BF3 OUT (EBH),A 0BF5 INC DE ... 0BFE LD (HL),B 0BFF INC HL 0C00 LD (HL),C

DE=3840h은 현재 「や」 Token 48 38에서 구성한 값과 일치합니다. E8h/E9h에 위치를 설정한 뒤 같은 포트에서 두 바이트를 읽고, 읽을 때마다 DE를 증가시키는 구조를 확인합니다.

여기서 출력 Code만 보는 것으로 충분할까요? 실제 IN 결과와 쓰기 직전의 BC를 확인해야 합니다.
07 · VERIFY GLYPH DATA

첫 두 행의 실제 Glyph 바이트와 출력 위치를 비교한다

QUASI88> break 0x0BFE #2 QUASI88> g *** Break at 0BFEH *** ( MAIN[#2] : PC ) [MAIN] BC:0000 DE:3841 HL:EBD4 PC:0BFE QUASI88> dump 0xEBD4 #4 EBD4 : FF FF FF FF FF FF FF FF FF FF FF FF FF FF FF FF QUASI88> step [MAIN] PC:0BFF HL:EBD4 QUASI88> step [MAIN] PC:0C00 HL:EBD5 QUASI88> step [MAIN] PC:0C01 HL:EBD5 QUASI88> dump 0xEBD4 #4 EBD4 : FF FF FF FF FF FF FF FF FF FF FF FF FF FF FF FF QUASI88> g *** Break at 0BE1H *** ( MAIN[#1] : PC ) [MAIN] BC:0000 DE:3841 HL:EC24 PC:0BE1 QUASI88> g *** Break at 0BFEH *** ( MAIN[#2] : PC ) [MAIN] BC:0180 DE:3842 HL:EC24 PC:0BFE
행읽기 시작 DE읽기 후 BC기록 직전 HL
1행3840h0000hEBD4h
2행3841h0180hEC24h

1행에서는 B=00h, C=00h입니다. 2행에서는 B=01h, C=80h이므로 0BFE / 0C00의 기록값도 두 행이 다릅니다. 두 행의 시작 주소 차이 EC24h−EBD4h=50h는 다음 화면 행으로 이동했다는 근거가 됩니다.

Monitor dump의 FF를 그대로 둔다

첫 행에서 LD (HL),B와 LD (HL),C를 실제로 step한 뒤에도 일반 dump는 FF를 표시했습니다. 이 출력 Code는 OUT (34H),07H, OUT (35H),80H를 이용한 그래픽 접근을 사용합니다. 일반 RAM dump와 GVRAM 기록이 동일하게 보인다고 단정하지 않습니다. 별도의 화면·GVRAM 검증은 후속 조사 항목입니다.

08 · VERIFY SCRIPT · 실험 대기

Script 첫 두 바이트만 바꿔 출력 문자가 변하는지 확인한다

이미 실제로 확인한 원본 Script는 969Fh : B8 62입니다. 기존 바리스 분석에서 20 18이 あ를 출력하는 Token으로 기록돼 있으므로, 이번 첫 이벤트 주소에서 실제로 RAM을 변경하는 시험을 별도로 수행합니다.

기존 확정값

원본 첫 Token: B8 62 → 「雨」
기존 분석의 Token: 20 18 → 「あ」

아직 필요한 증거

원본 dump → 정확한 QUASI88 write 명령과 실행 로그 → 첫 글자가 「あ」로 바뀐 실제 화면 → 원본 복원.

실습 기록 자리 — 아직 실행하지 않은 절차 1. 원본 게임 상태로 재시작하여 969Fh의 원본 B8 62 확인 2. QUASI88 write 명령의 실제 문법을 검증한 뒤 RAM 두 바이트만 수정 3. 재개 후 첫 글자와 나머지 문장 비교 4. 결과 화면 및 원본 복원 기록 보관

아직 성공 화면을 만들지 않는다

이 첫 이벤트 주소에서의 실제 RAM 변경·재개·출력 로그는 아직 확보되지 않았습니다. 강좌 완성 시 실측값으로만 이 단계를 채웁니다.

09 · VERIFY FONT · 실험 대기

Script는 그대로 두고 HxD로 「雨」의 Glyph 32바이트만 바꾼다

이벤트 첫 글자에서 B8 62 → DE=62B0h으로 Kanji ROM에 접근합니다. 재현 빌드의 KANJI1.ROM 레이아웃을 기준으로 한 32바이트 Glyph 슬롯 시작 후보는 62B0h × 2 = C560h입니다. 이 주소는 기존 별도 ROM 치환 실험에서도 사용됐지만, 이번 강좌의 HxD 수동 교체는 아직 미실시입니다.

항목값
원본 첫 문자 TokenB8 62 — 수정하지 않음
첫 문자 Kanji 접근62B0h
교체할 파일 범위0xC560~0xC57F (32 bytes)
「가」 bitmap 원천재현 빌드의 16×16 가 글리프

다음은 재현 빌드의 확정 글리프 TXT를 각 행의 상위·하위 바이트로 직렬화한 H﻿xD 교체용 32바이트 후보입니다. 실제 바리스 첫 이벤트에서의 HxD 치환 결과는 별도로 검증합니다.

00 08 1F C8 00 48 00 48 00 48 00 48 00 48 00 4E 00 88 01 08 01 08 02 08 04 08 04 08 18 08 00 08

원본 보호와 실험 구분

원본 KANJI1.ROM은 별도로 보관하고 복사본에서 Overwrite만 사용합니다. 파일 길이와 인접 Glyph가 변하지 않았는지 비교합니다. 재현 빌드에서 「가」의 정식 배치 주소 0x02F40은 이번 「雨」 슬롯의 임시 치환 주소 0xC560과 다릅니다. 동일 「雨」 Glyph를 사용하는 다른 출력도 함께 바뀔 수 있습니다.

실습 기록 자리 — 아직 확보하지 않은 증거 11. HxD 원본 0xC560~0xC57F 화면 12. 32바이트 Overwrite 후 같은 범위와 ROM 파일 길이 비교 13. 수정 ROM으로 완전 재시작 후 「가」 출력 화면
10 · FINISH AND RECORD

실측으로 확정된 사실과 예정 실험을 구분한다

왜 강제 Monitor에 들어갔을 때 PC=04BDh를 바로 출력 루틴으로 보지 않는가?
현재 PC는 단지 그 순간 실행 중인 위치입니다. 이번에는 0292h의 대기 루프였으며 Stack과 반환 주소를 통해 호출 관계를 찾아야 했습니다.
왜 「が」의 Token C8 18과 Stack의 저장된 DE=18D0h가 다른가?
Token에서 구성한 시작값은 18C0h입니다. 16개 Glyph 행을 읽으며 INC DE가 16번 실행돼 18D0h가 됩니다.
BC=0180h가 어떤 명령을 통해 쓰이는가?
0BFE LD (HL),B, 0BFF INC HL, 0C00 LD (HL),C입니다. 단, 일반 RAM dump가 동일한 값을 표시한다는 뜻은 아닙니다.
Script Token 변경과 ROM Glyph 변경은 무엇이 다른가?
전자는 선택되는 문자 코드 자체를 바꾸고, 후자는 기존 Token을 유지한 채 그 코드가 가리키는 bitmap만 변경하는 실험입니다.
