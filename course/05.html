FOUNDATION 05 · BEGINNER TRACE

화면에서 다음 조사 방향 찾기

《몽환전사 바리스》의 타이틀 화면을 예제로 삼아, 화면에서 질문을 만들고 관찰 결과에 따라 다음 조사 행동을 고르는 방법을 배웁니다.

이 강좌의 목표

이번 부의 목표는 《몽환전사 바리스》 타이틀 화면을 완벽하게 해독하는 것이 아닙니다. 화면에서 궁금한 현상을 발견했을 때 어디서 조사를 시작하고, 관찰 결과에 따라 다음에 무엇을 확인할지 정하는 방법을 배웁니다.

QUASI88 Monitor와 실제 분석 기록은 그 방법을 보여 주는 예제입니다. 다른 Debugger를 사용하더라도 관찰 → 판단 → 다음 행동이라는 순서는 같습니다.

관찰

화면에서 무엇이 언제 달라지는지 찾습니다.

판단

확인한 사실과 아직 확인하지 않은 추측을 구분합니다.

다음 행동

현재 질문에 맞는 Code·Memory 관찰 방법을 고릅니다.

01 · OBSERVE

분석은 명령어가 아니라 화면 관찰에서 시작한다

완성된 타이틀 화면만 보면 모든 요소가 한꺼번에 나타난 것처럼 보입니다. 그러나 진행 과정을 천천히 보면 서로 다른 요소가 차례로 추가됩니다.

관찰

한 화면도 한 번에 만들어지지 않습니다. 작은 글자, 영문 부제, 배경, 큰 로고가 서로 다른 시점에 나타납니다.

판단

각 요소가 서로 다른 Code에서 처리된다고 아직 확정할 수는 없습니다. 다만 출력 시점이 다르므로 조사 시점을 나눌 수 있다는 단서는 얻었습니다.

다음 행동

화면 전체를 한꺼번에 쫓지 않고, 가장 먼저 나타나는 작은 「夢幻戦士」만 조사 대상으로 고릅니다.

02 · ASK A SMALL QUESTION

큰 질문을 조사 가능한 질문으로 줄인다

“타이틀 화면은 어떻게 만들어지는가?”는 너무 넓은 질문입니다. 관련 Data, 배경, 애니메이션, 큰 로고와 크레딧을 모두 보게 되어 어디서 시작해야 할지 알기 어렵습니다.

질문문제점 또는 장점
타이틀 화면 전체는 어떻게 만들어지는가?범위가 너무 넓어 첫 조사 지점을 정하기 어렵습니다.
먼저 나타나는 작은 글자는 언제 처리되는가?관찰할 화면 요소와 실행 시점을 함께 제한할 수 있습니다.
그 순간 CPU는 어느 Memory를 처리하는가?Debugger로 확인할 수 있는 구체적인 질문입니다.
이번 사례의 출발 질문: 작은 「夢幻戦士」가 나타나는 동안 CPU는 어떤 Code와 Memory를 처리하는가?

화면의 글자가 반드시 문자열인 것은 아니다

사람 눈에는 글자로 보여도 내부에서는 문자 코드와 Font, 미리 그린 그림, 압축된 그래픽 Data 등 여러 방식으로 표현될 수 있습니다. 따라서 처음부터 문자열이라고 단정하지 않습니다.

다음 행동

작은 글자가 나타나는 도중 실행을 멈추고, 현재 CPU가 실행 중인 위치와 주변 Code부터 확인합니다.

03 · START FROM WHERE YOU STOPPED

정답 주소를 모르면 현재 실행 위치에서 시작한다

처음부터 특정 주소를 알고 있을 필요는 없습니다. 화면이 변하는 동안 Debugger로 들어가 CPU가 지금 어디에 있는지 확인합니다.

알고 싶은 것일반적인 기능QUASI88 예제
CPU가 지금 어디에 있는가?Register 보기reg
그 주변에 어떤 Code가 있는가?Disassembly 보기disasm #64
Register가 가리키는 byte는 무엇인가?Memory 보기dump 주소

실행 상태

타이틀이 진행되어 작은 글자가 나타나는 동안 Monitor로 들어갑니다. 멈추는 순간에 따라 PC는 달라질 수 있습니다.

reg disasm #64

실제 조사에서는 다음과 같이 PC=04DA 부근에 멈춘 기록을 얻었습니다.

PC:04DA HL:DAC4 BC:0150 IX:3300 04DA INC HL 04DB RR (HL) 04DD INC HL 04DE RR (HL) ... DEC B JP NZ,04B4 LD BC,0050 ADD HL,BC DEC IXH JP NZ,04AC

주소를 외우지 않는다

04DA는 이번 실행에서 관찰된 위치일 뿐입니다. 이 주소가 곧 작은 로고 routine의 시작이라는 뜻도 아닙니다. 다른 게임이나 다른 시점에서는 전혀 다른 주소에서 멈춥니다.

관찰

HL이 변하면서 HL이 가리키는 Memory를 반복 처리하고 있습니다.

판단

연속된 Data 또는 일정한 간격의 Memory 영역을 처리할 가능성이 있습니다. 아직 화면 출력 Code라고 확정할 수는 없습니다.

다음 행동

반복문 앞부분과 HL의 변화, 실제 Memory 쓰기를 확인합니다.

04 · LET CODE CHOOSE THE NEXT STEP

모든 명령을 해독하기보다 다음 단서를 찾는다

초보자가 처음 보는 Code를 한 줄도 빠짐없이 해석하려 하면 곧 막힙니다. 먼저 반복, 주소 변화, Memory 접근, 분기와 호출처럼 다음 조사 방향을 정하는 명령을 찾습니다.

보이는 특징알 수 있는 것다음에 확인할 것
INC HL 반복HL이 다음 byte를 차례로 가리킵니다.HL의 시작값과 가리키는 Memory
RR (HL) 반복HL이 가리키는 Memory 값이 변경됩니다.변경 전후 값과 실제 WRITE 위치
DEC B / JP NZ정해진 횟수만큼 안쪽 반복을 수행합니다.B의 시작값과 반복 범위
ADD HL,BCHL이 일정한 간격만큼 이동합니다.그 간격이 Data나 화면 배열과 관계있는지
CALL다른 routine으로 처리를 맡깁니다.호출된 routine에 들어가 무엇을 하는지

용어: pointer

Memory 주소를 담고 다른 위치를 차례로 가리키는 register를 pointer처럼 사용한다고 말합니다. 여기서는 HL이 그런 후보입니다.

주의: RR (HL)

단순한 오른쪽 이동이 아니라 Carry를 포함한 회전입니다. 지금 필요한 핵심은 세부 flag보다 HL이 가리키는 Memory를 읽고 같은 위치에 다시 쓴다는 사실입니다.

다음 행동

“이 Code가 실행되는가?”가 아니라 “이 Code가 실제로 어느 Memory를 바꾸는가?”가 다음 질문이므로 WRITE breakpoint를 선택합니다.

05 · CHOOSE THE EVENT

질문에 맞는 breakpoint를 고른다

breakpoint는 종류를 외우는 기능이 아니라, 알고 싶은 사건을 잡는 도구입니다.

현재 질문선택할 사건
이 routine은 언제 실행되는가?PC 또는 Execution breakpoint
이 Data를 어느 Code가 가져가는가?READ breakpoint
이 Memory를 어느 Code가 바꾸는가?WRITE breakpoint

이번 사례에서는 반복문이 Memory를 바꾸는지 검증하려고 WRITE를 사용했습니다. 기존 breakpoint가 남아 있으면 다른 곳에서 먼저 멈출 수 있으므로 조사 목적이 바뀔 때 정리합니다.

break clearall #0 break write 0xD4A1 #1 g
QUASI88 명령은 예제입니다. 다른 Debugger에서는 Memory write breakpoint 또는 watchpoint라는 이름을 사용할 수 있습니다.

실행 상태

타이틀을 처음부터 다시 진행하여 작은 글자가 나타나는 구간을 통과합니다.

기대할 결과

지정한 Memory에 WRITE가 발생하면 실행이 멈추고, 실제로 값을 쓴 명령과 주변 register를 확인할 수 있습니다.

중요

breakpoint가 걸렸다는 사실은 정답이 아니라 조사할 Code를 하나 발견했다는 뜻입니다.

06 · CHECK BEFORE CONCLUDING

걸린 Code의 역할을 주변 동작으로 판별한다

실제 조사에서는 화면 Memory로 보이는 D400 WRITE에도 breakpoint가 걸렸습니다. 주소만 보면 로고를 기록하는 Code처럼 보일 수 있습니다. 그러나 주변을 확인한 결과는 달랐습니다.

D400 WRITE에서 정지 ↓ 6344 부근의 LDIR 확인 ↓ 5C · 5D · 5E를 차례로 선택 ↓ 넓은 영역에 00을 반복 기록

관찰

세 GVRAM plane의 넓은 범위에 같은 값 00을 반복 기록했습니다.

판단

특정 로고 모양을 만드는 처리보다 화면을 지우는 초기화 동작에 가깝습니다.

다음 행동

이 후보를 로고 source 추적으로 계속 밀어붙이지 않고, 작은 글자가 실제로 그려지는 시점의 다른 WRITE와 호출 관계를 조사합니다.

핵심: breakpoint가 걸린 Code는 조사 후보일 뿐입니다. 주변 Code, 기록하는 값, 반복 범위와 화면 시점을 함께 확인한 뒤 역할을 판단합니다.
07 · EXPAND ONLY WHEN NEEDED

현재 Code만으로 부족할 때 호출 관계를 따라간다

현재 routine이 Memory를 처리한다는 사실은 알았지만 Data가 어디서 준비되었는지 알 수 없다면, 이 routine을 부른 쪽으로 조사 범위를 넓힙니다.

현재 Code돌아갈 주소호출자 주변CALL 대상

실제 사례에서는 stack에 저장된 byte F1 03을 확인했습니다. Z80은 16비트 값을 낮은 byte부터 저장하므로 반환 주소 후보를 03F1로 읽습니다. 그 주변에서 CALL 05AD를 확인하고, 다시 그 routine 안에서 공통으로 호출되는 061F를 다음 후보로 골랐습니다.

stack의 F1 03 → 반환 주소 후보 03F1 → 주변 Code에서 CALL 05AD 확인 → 05AD 안에서 CALL 061F 확인

주소는 학습 목표가 아니다

03F1, 05AD, 061F는 바리스의 실제 조사 기록입니다. 외울 것은 주소가 아니라 현재 Code의 바깥을 보고 싶을 때 stack과 CALL을 이용한다는 방법입니다.

왜 061F를 보았는가

05AD에서는 PC-88의 5C, 5D, 5E 포트를 차례로 사용하면서 같은 061F를 호출했습니다. 이 포트는 각각 GVRAM plane을 선택합니다. 포트를 선택하는 것만으로 그림이 그려지는 것은 아니므로, 공통 호출 안에서 실제 Memory WRITE가 일어나는지 확인하는 것이 다음 행동이 됩니다.

08 · CONNECT DATA AND CODE

입력 후보와 출력 후보를 같은 실행 안에서 확인한다

061F 실행 중 register를 기록하자 다음 값이 함께 관찰되었습니다.

HL' = 4405 HL = C50E IXH = 18

HL'은 H의 값이 아니라 Z80의 보조 register 묶음에 있는 16비트 HL 전체입니다. 이 값만 보고 역할을 단정하지 않고, 각각이 가리키는 Memory와 실제 접근을 확인합니다.

dump 0x4405 → 사람이 읽는 문자열이 아닌 byte열 061F 실행 중 C50E WRITE → 처리 중 출력 후보에 실제 기록 발생

관찰

4405 부근의 byte열과 C50E WRITE가 같은 routine 실행 안에서 함께 관찰됩니다.

판단

4405 부근은 입력 Data 후보이고 C50E 부근은 처리 결과가 기록되는 출력 후보입니다. source 형식 전체를 해독하지 않아도 Data·Code·Output 사이의 실행 관계는 확인할 수 있습니다.

다음 행동

처음 세운 질문에 필요한 관계가 확인되었는지 점검합니다. 그래픽 형식 자체가 목적이라면 Data 해독을 계속할 수 있지만, 이번 기초 강좌는 여기서 멈춥니다.

4405 부근 Data061F 처리C50E 부근 WRITE선택된 GVRAM plane
09 · KNOW WHEN TO STOP

처음 질문에 답했으면 필요한 범위에서 마무리한다

역분석은 모든 byte의 의미를 알아야만 끝나는 작업이 아닙니다. 처음 세운 질문에 답할 근거가 모였는지 확인하고, 목적에 따라 다음 범위를 결정합니다.

단계이번 사례에서 확인한 것
화면 관찰작은 글자가 다른 요소보다 먼저 나타났습니다.
현재 Code해당 시점에 Memory를 반복 처리하는 Code가 실행됐습니다.
실제 접근WRITE breakpoint로 Memory 변경을 검증했습니다.
후보 판별화면 초기화처럼 질문과 맞지 않는 후보를 주변 Code로 제외했습니다.
범위 확장stack과 CALL을 이용해 공통 처리 routine으로 이동했습니다.
관계 확인입력 Data 후보, 처리 Code, 출력 위치가 같은 실행 안에서 연결됐습니다.
이번 부의 결론: 타이틀 로고를 완벽하게 분석한 것이 아니라, 화면에서 질문을 만들고 현재 실행 위치에서 시작해 다음 조사 행동을 정하는 방법을 확인했습니다.

다른 게임에도 적용하는 기록법

관찰: 화면에서 무엇이 언제 달라졌는가? 판단: 현재 증거로 어디까지 말할 수 있는가? 다음 행동: 무엇을 확인해야 현재 판단을 검증할 수 있는가?

다음 화면 요소를 더 깊게 조사할지는 수강생이 목적에 따라 정합니다. 더 깊은 그래픽 형식 해독은 이제 수강생의 몫으로 남겨 둡니다.

10 · CHECK YOUR METHOD

주소가 아니라 조사 방법을 확인한다

1. 완성 화면보다 만들어지는 순서를 먼저 보는 이유는?
요소가 나타나는 시점을 나누면 조사 대상과 실행 시점을 작게 제한할 수 있기 때문입니다.
2. PC=04DA가 로고 routine의 시작 주소라고 바로 말할 수 없는 이유는?
PC는 Monitor에 들어간 순간의 현재 실행 위치일 뿐입니다. routine의 시작과 역할은 주변 Code와 실제 동작을 더 확인해야 알 수 있습니다.
3. PC·READ·WRITE breakpoint는 어떻게 고르는가?
실행 시점을 알고 싶으면 PC, Data를 누가 사용하는지 알고 싶으면 READ, 누가 값을 바꾸는지 알고 싶으면 WRITE를 고릅니다.
4. breakpoint가 걸린 뒤 가장 먼저 해야 할 일은?
걸린 주소를 정답으로 단정하지 말고, 실제 접근 명령과 주변 Code, register, 읽거나 쓴 값을 확인합니다.
5. 현재 routine의 바깥으로 조사를 넓히려면 무엇을 보는가?
stack의 반환 주소와 호출자 주변의 CALL을 확인합니다.
6. 이번 부가 4405의 전체 그래픽 형식을 해독하지 않고 끝나는 이유는?
