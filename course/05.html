PC-88 게임 분석 기초 강좌 / 5부
FOUNDATION 05 · LOG-DRIVEN TRACE

실제 로그에서 다음 조사 위치를 찾아가는 법

《몽환전사 바리스》 타이틀 화면의 실제 QUASI88 기록을 따라가며, 화면 관찰과 실행 로그를 근거로 다음 Code와 Memory를 선택하는 방법을 배웁니다.

이번 부의 목적

이번 부는 타이틀 그래픽을 완벽하게 해독하는 내용이 아닙니다. 수강생이 화면에서 질문을 만들고, 실제 실행 로그를 읽고, 그 로그가 가리키는 다음 조사 위치를 스스로 고르는 것이 목표입니다.

따라서 이 페이지에서는 결론만 보여주지 않습니다. 어떤 화면에서 멈췄는지, 어떤 명령을 실행했는지, 그 결과에서 왜 다음 주소를 조사했는지를 함께 보여줍니다.

실제 QUASI88 로그관찰 → 판단 → 다음 행동근거 기반 조사완전 해독 범위 아님
화면 관찰현재 PC 확인주변 Code 확장Memory 변화 검증호출자 추적공통 처리 확인필요한 지점에서 종료

이 부의 흐름

  1. 화면에서 조사 대상을 고른다
  2. 타이틀 화면에서 현재 PC와 주변 Code를 확인한다
  3. 관찰한 분기 주소를 따라 범위를 넓힌다
  4. Single-step으로 Memory 변화를 확인한다
  5. stack과 반환 주소로 호출자를 찾는다
  6. 발견한 주소를 실제 후보로 검증한다
  7. 공통 호출에서 다음 처리 Code를 고른다
  8. 입력 Data와 출력 위치를 연결한다
  9. 잘못 잡은 단서를 버리는 법
  10. 질문에 답했으면 멈춘다
  11. 확인 문제와 독립 과제
01 · OBSERVE

화면 전체가 아니라 먼저 나타나는 요소 하나를 고른다

완성된 타이틀 화면만 보면 모든 요소가 동시에 만들어진 것처럼 보입니다. 그러나 실제 진행 화면을 시간 순서로 비교하면 작은 일본어 제목, 영문 부제, 배경, 큰 로고와 크레딧이 서로 다른 시점에 나타납니다.

이번 조사 대상: 먼저 나타나는 작은 「夢幻戦士」가 어떤 Data와 Code를 거쳐 화면에 나타나는가?

관찰

화면 요소마다 나타나는 시점이 다릅니다.

판단

각 요소의 실행 시점을 따로 조사할 수 있다는 단서를 얻습니다.

다음 행동

주소를 추측하거나 디스크 전체를 뒤지지 않고, 오프닝 화면 처리 중 강제로 브레이크를 건 뒤 현재 CPU 위치부터 확인합니다.

02 · FIRST OBSERVATION

타이틀 화면에서 현재 PC와 주변 Code를 확인한다

오프닝 화면 처리 중 강제로 브레이크를 겁니다. 브레이크가 걸린 정지 시점에 먼저 reg로 register와 PC를 확인하고, 주소를 생략한 disasm #64로 현재 PC부터 이어지는 명령을 표시합니다. 이렇게 현재 실행 위치와 주변 명령에서 조사를 시작합니다.

게임 상태오프닝·로고 그래픽 처리 중 강제로 브레이크를 건 상태복사할 명령reg를 실행한 뒤 disasm #64로 현재 PC 주변을 확인정상적으로 볼 결과현재 PC와 그 주변의 반복·분기·Memory 접근 명령
break clearall #0 reg disasm #64

오프닝 화면 처리 중 강제로 브레이크를 겁니다. 정지 시점의 register 출력에서 PC=04DA를 확인합니다.

관찰

INC HL과 RR (HL)이 반복되고, 끝에서 JP NZ,04B4, JP NZ,04AC으로 되돌아갑니다.

판단

HL이 가리키는 Memory를 일정한 순서로 처리하는 반복 구조입니다. 아직 이것이 로고 처리 Code의 시작이라고 할 수는 없습니다.

여기서 하지 않는 판단

PC=04DA는 첫 브레이크가 걸린 현재 실행 위치입니다. 처리 Code의 시작 주소도, 작은 글자의 원천 주소도 아닙니다. 주변 명령과 호출 관계를 더 확인해야 역할을 판단할 수 있습니다.

현재까지 확인한 타이틀 구조

화면에서 시작했지만, 아직 Data의 위치나 처리 Code의 역할은 확정하지 않았습니다.

flowchart TD
  S["작은 夢幻戦士가 먼저 표시됨"] --> B["오프닝 화면에서 강제 브레이크"]
  B --> P["PC 04DA\nINC HL / RR (HL) 반복"]

다음 행동을 추론한다

DEC B 다음에 JP NZ,04B4가 있으므로, B가 안쪽 RR (HL) 반복 횟수를 관리한다고 가정할 수 있습니다. 이어서 ADD HL,0050H 뒤에 DEC IXH와 JP NZ,04ACH가 있으므로, 안쪽 반복이 끝나면 HL을 다음 줄 위치로 옮기고 IXH를 줄인 뒤 바깥 반복을 계속한다고 가정할 수 있습니다.

이 가정을 확인하려면 두 진입점 앞의 준비 명령, 즉 포트 선택·HL/DE 초기값·반복 카운터 설정을 함께 봐야 합니다. 주소를 생략한 출력은 04DA에서 시작하므로 준비 명령이 보이지 않습니다. 04AC보다 앞인 04A0부터 다시 확인합니다.

disasm 0x04A0 #72
03 · FOLLOW THE EVIDENCE

관찰한 분기 주소를 따라 범위를 넓힌다

앞 단계의 출력에서 두 종류의 반복이 보였습니다. 04B4는 DEC B가 남아 있을 때 되돌아가는 안쪽 반복의 시작점이고, 04AC는 ADD HL,0050H와 DEC IXH 뒤에 다시 들어가는 바깥 반복의 지점입니다. 따라서 다음 질문은 “각 반복에 들어가기 전에 어떤 값과 포트를 준비하는가?”가 됩니다.

추론 가정: B는 한 번의 가로 처리 반복 수, IXH는 바깥쪽 줄 반복 수, 0050H는 다음 처리 위치로 이동하는 간격일 가능성이 있다. 이 가정을 확인하기 위해 반복 진입점보다 앞의 Code를 함께 봅니다.
게임 상태타이틀 그래픽 처리 중. Monitor에서 조사 범위를 넓혀 보는 상태복사할 명령disasm 0x04A0 #72정상적으로 볼 결과반복문 진입 전의 포트 선택, 시작 주소 설정, 반복 횟수와 반복 처리 부분

가정과 맞는 관찰

04A1 OUT (5C),A로 plane을 선택하고, 04A3 LD IXH,48H로 바깥 반복 카운터를 준비합니다. 이어서 04A6 LD HL,D400H와 04A9 LD DE,D44FH가 처리 위치를 준비합니다.

아직 확인할 것

04B4의 반복이 실제로 어떤 Memory를 바꾸는지는 disassembly만으로 확정하지 않습니다. HL이 가리키는 byte를 실행 전후로 비교해야 합니다.

반복 구조를 읽는 법

준비 명령부터 반복, 종료까지 이어지는 하나의 Code 덩어리를 routine이라고 부르기도 합니다. 여기서는 용어를 외우는 것보다, RR (HL)가 반복되는 부분과 그 앞의 준비 명령을 나누어 보는 것이 중요합니다. 다음 Code를 고를 때는 반복 구조와 각 register의 변화를 함께 봅니다.

현재까지 확인한 타이틀 구조

04A0은 Data의 원천이 아니라, 반복에 들어가기 전 무엇을 준비하는지 확인하기 위해 넓힌 범위입니다.

flowchart TD
  S["작은 夢幻戦士가 먼저 표시됨"] --> B["강제 브레이크"]
  B --> P["PC 04DA / 반복 코드 관찰"]
  P --> J["JP NZ 04B4 / JP NZ 04AC"]
  J --> D["disasm 04A0"]
  D --> O["OUT 5C / HL D400 / IXH 설정"]
  O --> R["04B4 RR (HL) / INC HL 반복"]
현재 로그에서 다음에 확인할 것은 무엇일까요? RR (HL)가 실제 Memory를 바꾸는지를 확인해야 합니다.
04 · VERIFY WITH A REAL CHANGE

반복 명령의 의미를 실제 Memory 변화로 확인한다

04A0부터 다시 표시한 결과에서 04CB INC HL과 그 다음 04CC RR (HL)을 확인했습니다. 이 두 명령의 실제 동작을 확인하기 위해 04CB에 PC breakpoint를 설정하고, 리셋한 뒤 다시 실행합니다.

break clearall #0 break pc 0x04CB #1 reset g

리셋 후 다시 실행하면 04CB에서 정지합니다. 이때의 register 출력은 다음과 같습니다.

[MAIN] AF:0044[.Z...P..] BC:0150 DE:D8FF HL:D8DF IX:3900 PC:04CB I:00 IM:2 IFF:1 A':C47D[.Z.H.P.C] B':0050 D':0800 H':615A IY:E55C SP:00FE 04C9 CB1E RR (HL) ------> 04CB 23 INC HL 04CC CB1E RR (HL)
게임 상태PC=04CB에서 INC HL 직전 정지. HL=D8DF관찰 과정dump → s → reg → 다시 dump를 차례로 실행하며 각 시점의 PC·HL·Memory 값을 비교정상적으로 볼 결과첫 step은 HL만 증가하고, 다음 RR (HL) 뒤에는 대상 byte가 변함

다음은 Monitor에서 입력한 명령과 각 명령 직후의 출력이 이어지는 순서 그대로 재현한 로그입니다.

QUASI88>dump 0xD8D8 #16 D8D8 : 08 00 02 00 80 00 00 00 10 41 00 00 00 00 00 04 QUASI88>s QUASI88>reg [MAIN] AF:0044[.Z...P..] BC:0150 DE:D8FF HL:D8E0 IX:3900 PC:04CC 04CB 23 INC HL ------> 04CC CB1E RR (HL) QUASI88>dump 0xD8D8 #16 D8D8 : 08 00 02 00 80 00 00 00 10 41 00 00 00 00 00 04 QUASI88>s QUASI88>reg [MAIN] AF:0000[........] BC:0150 DE:D8FF HL:D8E0 IX:3900 PC:04CE 04CC CB1E RR (HL) ------> 04CE 23 INC HL QUASI88>dump 0xD8D8 #16 D8D8 : 08 00 02 00 80 00 00 00 08 41 00 00 00 00 00 04

관찰

HL=D8E0인 상태에서 RR (HL)을 실행한 뒤 D8E0의 값이 10에서 08로 바뀌었습니다.

판단

이 반복 Code는 HL이 가리키는 Memory를 실제로 읽고 같은 위치에 변경된 값을 기록합니다.

이제 확정할 수 있는 범위

04B4 이후의 반복은 D8xx 계열 그래픽 처리 영역을 비트 단위로 변형하는 동작과 연결됩니다. 하지만 이 Code가 어디서 호출되었고, 원천 Data가 어디에 있는지는 아직 남은 질문입니다.

현재까지 확인한 타이틀 구조

04CB는 첫 정지 위치가 아니라, 앞서 읽은 Code에서 고른 확인 지점입니다.

flowchart TD
  S["작은 夢幻戦士가 먼저 표시됨"] --> P["PC 04DA에서 반복 관찰"]
  P --> D["disasm 04A0 / 반복 준비 확인"]
  D --> K["04CB와 04CC 선택"]
  K --> B["PC breakpoint 04CB / reset / g"]
  B --> M["04CB INC HL -> 04CC RR (HL)"]
  M --> W["D8E0 값 10 -> 08"]

다음 행동

이 반복이 끝나는 위치에서 RET과 stack을 확인합니다. 먼저 04CB breakpoint를 지우고, routine 끝에 breakpoint를 새로 설정합니다.

break clear #1 break pc 0x053B #1 g
05 · FIND THE CALLER

stack의 반환 주소를 호출자 후보로 바꾼다

반복 Code의 끝인 053B RET에서 멈추면, RET이 stack에서 돌아갈 주소를 꺼내기 직전의 상태를 볼 수 있습니다. stack을 확인하면 현재 Code를 호출한 곳으로 이동할 단서를 얻을 수 있습니다.

[MAIN] AF:2A42[.Z....N.] BC:0050 DE:EACF HL:EA80 IX:0000 PC:053B I:00 IM:2 IFF:1 A':C47D[.Z.H.P.C] B':0050 D':0800 H':615A IY:E55C SP:00FE 0538 C2AC04 JP NZ,04ACH ------> 053B C9 RET dump 0x00F0 #32 00F0 : 09 24 47 D6 50 02 10 FF 0A 07 44 00 F9 04 F1 03 0100 : F3 31 00 01 CD 78 06 FB 11 00 22 CD 80 EC 30 05

little-endian으로 읽기

Z80의 16비트 반환 주소는 낮은 byte부터 stack에 저장됩니다.

stack byte: F1 03 낮은 byte: F1 높은 byte: 03 → 반환 주소 후보: 03F1

03F1을 routine 시작 주소로 사용하지 않습니다. “RET 뒤에 CPU가 돌아갈 후보 위치”로 사용해 그 주변을 disassemble합니다.

게임 상태그래픽 이동 routine의 RET까지 도달한 상태복사할 명령disasm 0x03D0 #128로 반환 주소 주변을 확인정상적으로 볼 결과03F1 앞에 현재 routine을 호출한 CALL이 나타남
disasm 0x03D0 #128 03D0 CDA104 CALL 04A1H 03D3 C1 POP BC 03D4 10F9 DJNZ 03CFH 03D6 D9 EXX 03D7 218E5D LD HL,5D8EH 03DA D9 EXX 03DB 21C5F6 LD HL,F6C5H 03DE 3E2A LD A,2AH 03E0 322006 LD (0620H),A 03E3 DD2618 +LD IXH,18H 03E6 CDAD05 CALL 05ADH 03E9 3E01 LD A,01H 03EB 327D08 LD (087DH),A 03EE CDA104 CALL 04A1H 03F1 3A7C08 LD A,(087CH) 03F4 3D DEC A 03F5 2007 JR NZ,03FEH 03F7 3E1E LD A,1EH 03F9 325007 LD (0750H),A 03FC 3E82 LD A,82H 03FE 327C08 LD (087CH),A 0401 3A6207 LD A,(0762H) 0404 B7 OR A 0405 2002 JR NZ,0409H 0407 18E5 JR 03EEH 0409 CDA90B CALL 0BA9H

이제 발견한 것

03EE CALL 04A1가 있고 그 다음 주소가 03F1입니다. stack에서 읽은 반환 주소와 실제 CALL이 맞습니다.

중요한 전환

03E6 CALL 05AD는 같은 상위 Code 블록에 보이는 별도 호출입니다. 반환 주소 자체는 아니지만, 타이틀 처리 후보 05AD를 실제 실행으로 확인할 근거가 됩니다.

현재까지 확인한 타이틀 구조

stack은 04A1의 호출 관계를 확인했고, 같은 상위 Code에서 다음 후보 05AD도 발견했습니다.

flowchart TD
  A["04CB에서 D8E0 변화 확인"] --> R["053B RET"]
  R --> ST["stack 00FE: F1 03"]
  ST --> RT["반환 주소 03F1"]
  C1["03EE CALL 04A1"] --> RT
  C2["03E6 CALL 05AD"] --> H["05AD를 다음 후보로 확인"]

단서가 다음 조사로 바뀌는 과정

04DA에서 첫 관찰04AC·04B4 역분기04CB에 breakpoint 설정리셋 후 D8E0 변화 검증RET와 F1 0303F1 주변 CALL05AD 발견

각 주소는 목록으로 외우는 값이 아니라, 앞 단계의 관찰에서 세운 가정을 확인하기 위해 다음 단계로 선택된 조사 지점입니다.

06 · VERIFY THE NEW CANDIDATE

발견한 주소가 실제 화면 처리와 관계있는지 확인한다

05AD를 발견했다고 바로 정답으로 확정하지 않습니다. 먼저 주변 Code에서 어떤 준비와 반복이 있는지 읽고, 타이틀 표시 시 실제로 실행되는지 확인합니다.

게임 상태03D0 주변에서 CALL 05AD를 발견한 상태복사할 명령break clearall #0 후 break pc 0x05AD #1, 계속 실행정상적으로 볼 결과타이틀 그래픽 표시 중 05AD에서 정지하고, 반복에 따라 register가 변함
break clearall #0 break pc 0x05AD #1 g

계속 실행하면 05AD에서 다시 정지하고, 내부 row가 바뀔 때마다 같은 지점이 반복해서 나타납니다.

*** Break at 05ADH *** ( MAIN[#1] : PC ) [MAIN] AF:FF02[......N.] BC:0000 DE:0000 HL:C5FE IX:1500 PC:05AD A':C47D[.Z.H.P.C] B':0050 D':0800 H':4495 IY:E55C SP:00FE 05CA C2AD05 JP NZ,05ADH ------> 05AD D35C OUT (5CH),A 05AF E5 PUSH HL 다음 hit *** Break at 05ADH *** ( MAIN[#1] : PC ) [MAIN] AF:FF02[......N.] BC:0000 DE:0000 HL:C64E IX:1400 PC:05AD A':C47D[.Z.H.P.C] B':0050 D:0800 H':44BF IY:E55C SP:00FE 05CA C2AD05 JP NZ,05ADH ------> 05AD D35C OUT (5CH),A

관찰

IX가 1500에서 1400으로 줄고, MAIN HL과 보조 H'도 이동합니다. 즉 05AD는 단순한 한 번짜리 호출이 아니라 여러 row를 처리하는 반복 routine입니다.

다음 행동

이제 05AD의 주변을 disassemble해 같은 routine 안에서 공통으로 호출되는 Code가 있는지 찾습니다.

disasm 0x05AD #80
07 · FOLLOW A COMMON CALL

공통으로 반복되는 호출을 보고 다음 routine을 고른다

05AD 주변에서 다음과 같은 반복 구조를 확인합니다.

05AD D35C OUT (5CH),A 05AF E5 PUSH HL 05B0 CD1F06 CALL 061FH 05B3 E1 POP HL 05B4 D35D OUT (5DH),A 05B6 E5 PUSH HL 05B7 CD1F06 CALL 061FH 05BA E1 POP HL 05BB D35E OUT (5EH),A 05BD E5 PUSH HL 05BE CD1F06 CALL 061FH 05C1 E1 POP HL 05C2 D5 PUSH DE 05C3 115000 LD DE,0050H 05C6 19 ADD HL,DE 05C7 D1 POP DE 05C8 DD25 +DEC IXH 05CA C2AD05 JP NZ,05ADH 05CD C9 RET

1부와 연결

5C, 5D, 5E는 PC-88 GVRAM plane을 선택하는 포트입니다. 포트 선택만으로 그림이 생기는 것은 아닙니다.

반복 구조

같은 061F를 세 plane에서 호출하고, HL += 50H, IXH-- 뒤 다시 05AD로 돌아갑니다.

다음 조사 주소는 어떻게 고를까요? 세 plane에서 공통으로 호출되는 061F가 실제 Data 처리와 WRITE를 담당하는지 확인합니다.
게임 상태05AD 구조에서 공통 CALL 061F를 발견한 상태복사할 명령break clearall #0 후 break pc 0x061F #1, 계속 실행정상적으로 볼 결과061F 진입 시 입력 후보·출력 후보가 register에 함께 나타남
break clearall #0 break pc 0x061F #1 g

05AD에서 같은 호출이 세 plane에 반복되므로, 그 호출 대상인 061F가 실제 한 줄 Data를 처리하는지 확인하는 순서가 됩니다. 다음 절에서는 이 가정을 register와 입력 Data dump로 확인합니다.

현재까지 확인한 타이틀 구조

05AD는 세 plane을 선택하고 같은 처리 Code를 반복 호출합니다. 이제 확인할 대상은 세 번 공통으로 호출되는 061F입니다.

flowchart TD
  U["03E6 CALL 05AD"] --> H["05AD row 반복"]
  H --> P1["OUT 5C"]
  H --> P2["OUT 5D"]
  H --> P3["OUT 5E"]
  P1 --> C["각 plane에서 CALL 061F"]
  P2 --> C
  P3 --> C
  C --> N["HL + 50 / IXH 감소 / 05AD 반복"]
08 · CONNECT INPUT AND OUTPUT

한 번의 실행에서 입력 Data 후보와 출력 후보를 함께 본다

061F에서 정지했을 때의 register와 주변 Code를 함께 확인합니다.

[MAIN] AF:1900[........] BC:005C DE:0000 HL:C50E IX:1800 PC:061F I:00 IM:2 IFF:1 A':C47D[.Z.H.P.C] B':0050 D':0800 H':4405 IY:E55C SP:00FA (ck=40239918) 05B0 CD1F06 CALL 061FH ------> 061F 0619 LD B,19H 0621 D9 EXX

이 값들을 바로 확정된 역할로 읽지 않고, 각각이 가리키는 방향을 확인합니다.

관찰값이 단계에서의 질문다음 확인
HL=C50E이 주소는 읽는 곳인가, 쓰는 곳인가?061F의 LD (HL),A와 출력 Memory 확인
보조 HL'=4405이 주소의 byte열은 사람이 읽는 문자열인가?dump 0x4405 #0x80
IXH=18H반복 높이 또는 row 수와 관계있는가?05AD에서 row마다 줄어드는지 비교

보조 register 설명

H'=4405처럼 보이는 값은 보조 register 묶음의 16비트 HL'입니다. 보조 HL의 상위 byte만을 뜻하지 않습니다. EXX가 현재 register 묶음과 보조 묶음을 교환합니다.

게임 상태PC=061F, HL=C50E, 보조 HL'=4405에서 정지한 상태복사할 명령dump 0x4405 #0x80와 disasm 0x061F #128정상적으로 볼 결과입력 Data 후보는 문자열이 아닌 byte열이고, 보조 HL에서 읽은 값이 MAIN HL 쪽에 기록되는 구조

관찰과 판단

보조 HL에서 읽은 byte열은 사람이 읽는 일본어 문자열이 아니라 처리 입력 후보입니다. 061F에는 LD (HL),A가 있으므로 MAIN HL=C50E는 출력 후보로 볼 수 있습니다.

여기서 입력 byte열의 전체 형식을 해독하지 않습니다. 이번 부의 목적은 입력 Data 후보 → 처리 Code → 출력 후보의 관계를 같은 실행 안에서 확인하는 것입니다.

현재까지 확인한 타이틀 구조

세 plane에서 공통으로 호출된 061F 안에서 보조 HL의 입력 후보와 MAIN HL의 출력 후보가 함께 관찰됐습니다.

09 · REJECT A FALSE LEAD

breakpoint에 걸렸다고 답을 찾은 것은 아니다

실제 조사에서는 D400 WRITE에도 breakpoint가 걸렸습니다. 화면 그래픽과 관련된 주소처럼 보이지만, 주변 Code를 확인하기 전에는 역할을 확정할 수 없습니다.

게임 상태타이틀 화면이 시작되기 전부터 D400에 어떤 Code가 쓰는지 감시할 상태복사할 명령기존 breakpoint를 지우고 D400 WRITE를 설정한 뒤 실행정상적으로 볼 결과쓰기 명령이 실행되는 순간 PC와 실제 기록 값을 확인
break clearall #0 break write 0xD400 #1 g
*** Break at 6346H *** ( MAIN[#1] : WRITE addr=D400H, data=00H ) [MAIN] AF:0044[.Z...P..] BC:2BF8 DE:D401 HL:D400 IX:FFFF PC:6344 I:F3 IM:2 IFF:0 A':FFFF[SZ.H.PNC] B':FFFF D':FFFF H':FFFF IY:FFFF SP:E5EE 6344 EDB0 LDIR ------> 6344 EDB0 LDIR 6346 D35F OUT (5FH),A

주변 Code는 다음처럼 확인됐습니다.

6334 F3 DI 6335 0600 LD B,00H 6337 ED79 OUT (C),A 6339 2100C0 LD HL,C000H 633C 3600 LD (HL),00H 633E 54 LD D,H 633F 5D LD E,L 6340 13 INC DE 6341 01F83F LD BC,3FF8H 6344 EDB0 LDIR 6346 D35F OUT (5FH),A 6348 FB EI 6349 C9 RET 631A AF XOR A 631B D353 OUT (53H),A 631D 0E5C LD C,5CH 631F CD3463 CALL 6334H 6322 0E5D LD C,5DH 6324 CD3463 CALL 6334H 6327 0E5E LD C,5EH 6329 CD3463 CALL 6334H

관찰

LDIR가 00을 넓은 영역에 반복 기록하고, 5C·5D·5E 세 plane에서 같은 처리 Code가 호출됩니다.

판단

특정 로고 입력 Data를 전개하는 Code보다 GVRAM plane을 비우는 초기화 처리에 가깝습니다.

이 단서에서 이동한다

D400 WRITE에 걸렸다는 이유만으로 로고 원천 Data라고 결론 내리지 않습니다. 주변 Code와 기록 값, 반복 범위를 확인했으므로 이 후보는 “화면 초기화”로 분류하고, 작은 「夢幻戦士」 표시와 직접 연결되는 다른 실행 경로로 이동합니다.

제외한 후보도 구조에 기록한다

D400 WRITE는 화면 처리와 관계있지만, 이번 질문의 입력 Data 후보나 전개 Code는 아니었습니다.

flowchart TD
  W["D400 WRITE breakpoint"] --> L["6344 LDIR"]
  L --> Z["00을 넓은 범위에 기록"]
  Z --> P["5C / 5D / 5E plane에서 반복"]
  P --> X["GVRAM plane clear\n작은 夢幻戦士 처리 후보에서 제외"]

10 · KNOW WHEN TO STOP

처음 질문에 답했으면 필요한 범위에서 멈춘다

이번 부의 질문은 타이틀 그래픽 전체의 압축 형식을 해독하는 것이 아니었습니다. 작은 「夢幻戦士」가 어떤 처리와 관계있는지 조사하는 것이었습니다.

조사 단계실제 로그에서 얻은 근거이번 부에서의 역할
화면 관찰작은 일본어 그래픽이 다른 요소보다 먼저 나타남조사 대상을 작게 제한
현재 위치첫 정지에서 PC=04DA, INC HL·RR (HL) 반복주소를 모른 채 실행 중인 Code에서 시작
범위 확장JP NZ,04B4, JP NZ,04AC 발견disasm 0x04A0 #72을 선택
실행 검증D8E0: 10 → 08Memory를 실제로 변경하는 처리임을 확인
호출자 추적F1 03 → 03F1, 주변에서 CALL 05AD05AD를 결과가 아니라 발견된 후보로 조사
공통 처리5C·5D·5E → CALL 061F061F를 다음 조사 지점으로 선택
Data·Output 연결HL'=4405, HL=C50E, LD (HL),A입력 Data 후보와 출력 후보를 같은 실행에서 연결
후보 판별6344 LDIR가 넓은 영역에 00 반복 기록로고 전개가 아닌 plane clear로 제외

이번 조사에서 누적된 타이틀 구조

실선은 실제 실행 로그로 연결한 흐름이고, 점선은 조사했지만 제외한 후보입니다.

flowchart TD
  S["작은 夢幻戦士 표시"] --> P["PC 04DA / 반복 관찰"]
  P --> D["04A0 범위 확장"]
  D --> B["04CB breakpoint / reset / g"]
  B --> M["D8E0: 10 -> 08"]
  M --> R["053B RET / F1 03 / 03F1"]
  R --> H["03E6 CALL 05AD"]
  H --> C["5C / 5D / 5E -> CALL 061F"]
  C --> O["HL' 4405 -> 061F -> HL C50E"]
  P -. "별도 WRITE 조사" .-> X["D400 / 6344 LDIR / plane clear"]
이번 부에서 확인한 답: 작은 「夢幻戦士」 표시와 연결된 실행에서 보조 HL'=4405의 입력 Data 후보, 061F 처리 Code, MAIN HL=C50E의 출력 후보, 그리고 05AD의 세 plane 반복을 확인했습니다. 이것은 그래픽 형식 전체를 해독했다는 뜻이 아니라, 처음 질문에 필요한 Data·Code·Output 관계를 실제 실행으로 좁혔다는 뜻입니다.

더 깊이 들어가면 4405~47E2 입력 Data의 호출 단위와 처리 형식, Disk loader까지 조사할 수 있습니다. 그러나 그것은 이번 기초 강좌의 필수 도달점이 아닙니다.

11 · CHECK AND APPLY

주소가 아니라 판단 과정을 연습한다

1. 왜 완성된 타이틀 화면보다 요소가 나타나는 순서를 먼저 보는가?
조사 대상을 화면 전체에서 먼저 나타나는 요소 하나로 줄이고, 그 요소가 나타나는 실행 시점을 따로 볼 수 있기 때문입니다.
2. 첫 정지에서 보인 PC=04DA가 로고 처리 Code의 시작 주소라고 할 수 없는 이유는?
PC는 첫 브레이크가 걸린 현재 실행 위치일 뿐입니다. 앞쪽 준비 Code와 호출 관계를 확인해야 처리 범위와 역할을 판단할 수 있습니다.
3. disasm 0x04A0 #72은 어떻게 유추했는가?
현재 출력의 끝에서 04AC와 04B4로 되돌아가는 분기를 발견했기 때문에, 두 반복문 진입점과 앞의 준비 명령을 함께 보기 위해 범위를 앞쪽으로 넓혔습니다.
4. D8E0의 10 → 08 변화가 중요한 이유는?
RR (HL)가 설명처럼 보이는 명령이 아니라 실제 HL 대상 Memory를 변경했다는 실행 증거이기 때문입니다.
5. stack의 F1 03을 왜 03F1로 읽는가?
Z80의 16비트 값이 낮은 byte부터 저장되는 little-endian 방식이기 때문입니다. 다만 03F1은 routine 시작 주소가 아니라 RET 뒤 복귀할 위치 후보입니다.
6. 03E6 CALL 05AD를 발견한 뒤 무엇을 확인해야 하는가?
실제로 타이틀 표시 시 05AD가 실행되는지 breakpoint로 확인하고, 주변 Code에서 어떤 공통 routine을 호출하는지 조사해야 합니다.
7. 왜 05AD 다음에 061F를 조사하는가?
세 GVRAM plane을 선택하는 각각의 구간에서 같은 061F를 호출하므로, 실제 Data 처리와 기록이 공통 호출 안에 있을 가능성을 확인하기 위해서입니다.
8. D400 WRITE가 로고 입력 Data 처리라고 판단하지 않은 근거는?
주변의 6344 LDIR가 넓은 영역에 같은 00을 반복 기록하고, 5C·5D·5E 세 plane에서 같은 clear 처리 Code가 호출됐기 때문입니다.
